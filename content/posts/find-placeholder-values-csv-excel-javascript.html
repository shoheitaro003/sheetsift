Your import requires an email in every row, and the check is if (!row.email). A customer's file has N/A in some rows, - in others and a few cells with only spaces. All of them pass, and your database now holds contacts whose email is the text "N/A".

By the end of this post you will have cellStatus(value), which tells a real value from a blank cell, a placeholder or a formula error, and checkRecords(records, columns), which turns that into row-by-row errors for required columns and notes for optional ones. You will also see why reading an .xlsx file with sheet_to_json hides formula errors, and how to read them. Every function and every result quoted below is checked by our test file in Node 22 with SheetJS 0.20.3.

Why a truthy check is not enough

{{code:PH_PROBLEM}}

A required-field check usually asks "is there a string here?". People who fill in spreadsheets answer a different question: "what do I type when I do not know?". The answer is a placeholder, text that stands for "no value", and it is a non-empty string, so every check above passes.

Data tools in other languages handle part of this for you. pandas' read_csv, for example, treats an empty string, "NaN", "N/A" and "NULL" as missing by default, plus what its documentation calls "other common representations of missing data" (pandas 3.1.1 documentation, read 2026-11-19). In a JavaScript importer you write that list yourself, so you also decide what is on it.

Step 1: tell values from placeholders

cellStatus sorts a cell into one of four groups. Blank is nothing, or only whitespace.

Placeholder is a word from a fixed list, or a cell made only of punctuation such as - or ?. Formula error is text like #REF! that a spreadsheet shows when a formula fails; in a CSV export it arrives as plain text. Everything else is a value.

{{code:PH_STATUS}}

Why each rule is there:

  • Whole cells only. The list is compared with the entire cell, so none of the above, Nina and n/a/b stay values. Before the comparison, spaces are removed, then brackets at the start and end and dots or question marks at the end, so N / A, (None), [blank], N/A. and TBD? all match.
  • Punctuation, not symbols. \p{P} is the Unicode punctuation category. It holds hyphens, dashes, dots, question marks, slashes, the asterisk and the underscore, and also #, %, @, & and quote marks, so a cell holding only one of those is a placeholder too. Spaces are removed first, so - - counts. Currency signs, +, ~ and | are symbols, not punctuation, so a lone $ stays a value. -5 has a digit, so it is a value too.
  • Formula errors are separate because the fix is different, and they are checked first. A placeholder means the person had no value; #REF! means the file had one and a broken formula lost it. The second half of the pattern accepts any name that starts with a letter and ends in ! or ?, so error names that are not in the list are still caught. The match ignores case, so a hand-typed #n/a is caught; the price is that a cell that holds only a hashtag ending in !, such as #Hello!, is a formula error too.
  • Numbers and booleans are values. 0 and false are answers, not gaps. The number NaN is the exception: it becomes the text "NaN", which is on the list.

Step 2: when a placeholder is a real value

Some placeholders are real data in one column. NA is the two-letter region code for Namibia: in Node 22, new Intl.DisplayNames("en", { type: "region" }).of("NA") returns "Namibia". Treat it as missing in a country column and you reject every customer there.

That is what the allowed argument is for. It is a list per column, compared exactly after trim(), so ["NA"] lets NA through but still flags na and N/A. Keep the list short and per column: allowing NA everywhere would let it through in the email column too. If a column has a fixed set of codes, such as countries, validate against that set instead; then the placeholder check only has to catch the gaps.

Step 3: errors for required columns, notes for the rest

A blank or placeholder in a required column must be fixed before import. In an optional column it should become a real empty value (null), so "n/a" does not end up in your database as text, and the user should see that it happened. A formula error is always an error, required or not, because a value existed and was lost.

{{code:PH_CHECK}}

Three choices in checkRecords are worth knowing:

  • rows holds every row that was checked, including rows with errors, so you can show them in a preview. Import them only when no problem has level "error".
  • Empty rows are skipped, not reported as missing values. Spreadsheets often end with blank rows, and reporting each as "email is empty" buries the real problems. A row is skipped if every configured column is blank; columns you did not configure are not looked at. skipped lists the row numbers, so you can mention blank rows in the middle of the data, which can mean a paste went wrong. A row of dashes is not skipped: someone typed them, so they are reported.
  • A file with no data rows is an error, so a header-only file does not import as a silent success.

Step 4: read Excel error cells with SheetJS

In an .xlsx file, a failed formula is not text. The cell has type "e" and a numeric error code. In our test with SheetJS 0.20.3, sheet_to_json returns such a cell as an empty value, for all eight error codes the test writes: with defval: null you get null; with defval: "" you get "", except for #NULL!, which comes back as null. This holds with header: 1 or without it, with raw: false or without it.

So #REF! in a required column reaches your check as "empty", and the user is told to fill in a cell that already shows an error. sheet_to_csv writes the error text instead.

The fix is to read the cells yourself and use the error's text, which SheetJS stores in the cell's w property. If w is ever missing, the fallback #ERROR! is still reported as a formula error.

{{code:PH_SHEETJS}}

Our test writes eight error codes into an .xlsx file with SheetJS, reads it back with readRecords, and checks that each one arrives as its text (#NULL!, #DIV/0!, #VALUE!, #REF!, #NAME?, #NUM!, #N/A, #GETTING_DATA) and that cellStatus reports it as a formula error. The same function reads a CSV, and there the option raw: true matters twice. Without it, our test shows SheetJS reading the text #N/A in a CSV as an error cell, so sheet_to_json drops it just as it does in an .xlsx file. With it, #N/A stays a string; readRecords returns "#N/A" either way.

raw: true also stops other conversions in text formats: without it, our test shows SheetJS turning 0123 into the number 123 and TRUE into true. In our .xlsx test, numbers still arrive as numbers with it. In an .xlsx file, a date cell's v is a serial number; our post on reading Excel dates shows how to convert it.

A quoted empty cell ("") in a CSV arrives as an empty value. Rows with no cells at all come back with every field "", which checkRecords then skips.

readRecords reads only the first sheet and assumes the headers are in the first row and match your names exactly. Before calling checkRecords, check that every required column was found: if Email is spelled E-mail in the file, every row would be reported as having an empty email, or skipped as empty, instead of one clear "column not found" message. Real files often have title rows above the headers and headers spelled many ways; our posts on finding the header row and mapping columns to your fields cover both.

What this does not cover

  • Invisible characters. trim() does not remove a zero width space, so a cell holding only U+200B is a "value" here. Run the cleaning from our post on invisible characters first.
  • Sentinel values such as 0, 999 or 1900-01-01 that some systems write for "unknown". They are valid numbers and dates, so only a rule for that column can catch them, for example "a birth date before 1901 is an error".
  • Placeholders in other languages. The list is English. Add the words your users type, in lower case without spaces.
  • What a dash means in a number column. - is a placeholder here. If your users' files use it for zero, treat that column separately.
  • Short names. Placeholders match in any case and without spaces, so a person whose name is written Nan, Na or Null is flagged. In name columns, make this a warning the user can dismiss rather than an error, or add the names to allowed.
  • Merged cells and repeated headers. In a merged cell only the top-left cell holds the value, so the other rows read as empty and are flagged. Two columns with the same header map to one field, and the last one wins. Check for both when you read the sheet if your users' files have them.
  • Single letters. If your users' files use x for "none", add it per column; on a shared list it would also catch real values such as a size.
