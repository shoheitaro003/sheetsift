title: Read Excel dates in JavaScript without off-by-one-day bugs description: Excel stores dates as serial numbers. Tested SheetJS code that turns them into ISO dates with no time zone shift and no 1900 or 1904 date system errors. date: 2026-11-09 ---

A customer uploads an .xlsx file and the date column arrives as 46027. You convert it, and it shows as 4 January for users in California and 5 January in Tokyo. Or the whole column is four years and one day off, because the file came from an old Mac.

This post shows where each of these errors comes from, then builds three small functions that turn every date cell into ISO 8601 text (2026-01-05, 2026-01-05T13:30:00, 18:00:00) that is the same on every machine. Cells that cannot be a real date come back with a reason instead of a wrong value. Every result quoted below is checked by our test file with SheetJS 0.20.3 on Node, in several time zones.

What is actually in a date cell

An Excel date is a number, the serial number: the count of days since the start of the workbook's date system. The time of day is the fraction (0.5 is noon). What makes the cell look like a date is its number format, a code such as dd/mm/yyyy stored next to the number. So to read a date you need three things: the number, the format code and the workbook's date system.

Stored numberFormat codeMeans
46027yyyy-mm-dd2026-01-05
46027.5625dd/mm/yyyy hh:mm2026-01-05 13:30
0.75h:mm AM/PM6:00 PM, no date

Two date systems exist. In the default 1900 system, day 1 is 1 January 1900. In the 1904 system, day 0 is 1 January 1904, and the same date has a serial number 1,462 lower. Microsoft says the 1904 system was the default in earlier versions of Excel for Mac, and that it is a setting of each workbook (Date systems in Excel, Microsoft Support, updated June 2026). Old files and files saved from them can still use it.

The 1900 system also has a deliberate bug. Lotus 1-2-3 assumed 1900 was a leap year, and Excel kept that assumption so its serial numbers matched Lotus (Excel incorrectly assumes that the year 1900 is a leap year, Microsoft Learn, updated 30 March 2026). Serial 60 is the fake 29 February 1900, and every serial after it is one day ahead of a plain day count.

Three ways to get it wrong

1. The one-line formula

The formula you usually find converts the serial number to a JavaScript Date. The Date it builds is midnight in UTC. Read it with local-time methods and every user west of UTC sees the day before:

{{code:XD_FORMULA}}

It also ignores the 1904 system, and it is one day off for serials below 60, before the fake leap day.

2. SheetJS cellDates

SheetJS stores dates as numbers by default. With cellDates: true it creates Date objects, and handles the 1904 system for you. But the same file gives different Date values depending on how you read it and where the code runs:

{{code:XD_CELLDATES}}

With cellDates, cell.v is a Date at midnight UTC. sheet_to_json builds a new Date at midnight in the local time zone, unless you pass UTC: true. The SheetJS docs describe both: the date epoch "is based on the system timezone", and UTC makes dates "correct when interpreted in UTC" (SheetJS: Dates and Times, updated 3 August 2026). A server in UTC and a browser in Tokyo can therefore store different days. And serial 60 stays a number, so code that expects a Date in a date column fails on it.

If you already use sheet_to_json and only need the day to stop moving, this is the smallest fix. Pass UTC: true and read the result with UTC methods only:

{{code:XD_QUICKFIX}}

It still leaves serial 60 as a number, turns time-only cells into dates in December 1899, and does not tell dates from durations. The rest of this post handles those.

3. Dates in CSV files

A CSV has no format codes, only text. By default SheetJS tries to read text that looks like a date, in US order, and leaves what it cannot read as text:

{{code:XD_CSV}}

Here 03/04/2026 was probably 3 April, since the next row is day-first. The raw option turns this off for CSV and other text formats, and has no effect on XLSX, XLSB or XLS (SheetJS: Reading Files, updated 3 August 2026). With raw, every CSV cell is text, numbers included ("12.5"). Deciding the order of text dates is a separate problem, covered in why CSV importers break on real Excel files, and text numbers in parsing European number formats.

Step 1: tell date formats from number formats

Since the number alone does not say "date", the format code decides. A code is a date if it contains day or year letters, a time if it contains hours or seconds, and a duration if the hours, minutes or seconds are in square brackets ([h]:mm keeps counting past 24 hours). Before looking for letters, remove the parts that are not codes: quoted text such as "Due ", escaped characters, color and locale tags such as [Red] and [$-409], and AM/PM.

{{code:XD_KIND}}

A lone m is ambiguous: it means minutes next to hours or seconds, and months otherwise, so mmmm is a month and mm:ss is a time. For the 32 format codes in our tests, including yyyy"年"m"月"d"日", #,##0.00 "€" and _(* #,##0_), the function agrees with SheetJS's own XLSX.SSF.is_date on whether the code is a date, and adds which kind it is.

Step 2: convert the serial number with plain arithmetic

The conversion never creates a local-time Date. It counts days from the start of the date system in UTC and only formats the result, so the time zone of the machine cannot change it. The leap-year bug is handled in two lines: serial 60 is rejected, and serials after it move back one day.

{{code:XD_SERIAL}}
  • Times are rounded to the nearest second. In the stored number for 2026-01-05 14:30, the fraction times 86,400 is 52,199.99…, so cutting off the decimals gives 14:29:59, as it does for 704 of the 1,440 minutes of that day.
  • Dates drop the time part instead of rounding it. So 46027.9999999 is 2026-01-05 under a date format and 2026-01-06T00:00:00 under a date-time format. Only float noise (46027.99999999999, a formula result) is snapped to the next day first. SheetJS's formatter gives the same results.
  • Time formats drop the date. 46027.75 shown as h:mm comes back as 18:00:00, because that is all the cell shows. If you need the day too, ask for a date-time format in your template.
  • Day 0 is an error. SheetJS formats it as 1900-01-00. A time-only value under a date-time format (0.5 as yyyy-mm-dd hh:mm) falls on day 0 too, and is flagged rather than dated 31 December 1899.
  • The last valid day is 9999-12-31, the latest date Microsoft lists for Excel (Excel specifications and limits, Microsoft Support, updated June 2026).

Our tests compare serialToISO with the SheetJS formatter for 20,000 random serial numbers, in both date systems and for date, date-time and time output. They give the same text every time.

SheetJS also has XLSX.SSF.parse_date_code(serial, { date1904 }), which returns the year, month, day and time as numbers, and cell.w, the text Excel would show. Both are fine for display. Neither tells you a cell is a date in the first place, and both turn serial 60 into 29 February 1900 without a warning, which is why step 2 does its own arithmetic.

Step 3: read the workbook

Three read options do the work. cellNF: true keeps each cell's format code in cell.z; without it, our tests show z is missing. Leaving out cellDates keeps dates as serial numbers, so no time zone applies. And raw: true stops CSV dates from being guessed. The date system comes from workbook.Workbook.WBProps.date1904. Without cellDates, the SheetJS docs say all parsers "generate number cells" for dates (Dates and Times), so no Date object reaches readCell.

{{code:XD_READ}}

Each cell becomes { value }, plus kind for date and time cells and problem for cells your user needs to look at. The problem text includes the cell address (C8), so you can show it next to the row it belongs to. What comes back, from the test workbook:

The date-time value has no time zone suffix on purpose: as the SheetJS page above notes, Excel has no universal time, so a cell holds the clock time the author typed, with no zone attached. If you need an instant, take the zone from your user, for example as a setting on the import screen, and apply it on purpose.

Be careful when you turn these strings back into Date objects. JavaScript reads new Date("2026-01-05") as midnight UTC, but new Date("2026-01-05T13:30:00") as 13:30 in the local time zone. Our tests check both. If you only need the day, keep the string.

What this does not cover

  • Dates stored as plain numbers with the General format, as some scripts and libraries write them. They come back as 46027. If a column's name says date, flag it for your user instead of converting it silently.
  • Dates typed as text inside an .xlsx (05.01.2026 stored as text, not as a number). They come back unchanged; parse them like CSV dates, with the column's order decided from all its values.
  • Format codes with conditions such as [<1]hh:mm;yyyy-mm-dd. Step 1 reads only the first section, so check these by hand if your users' files have them.
  • The e year code and calendar codes for other eras. SheetJS treats e as a date; step 1 does not, because it cannot be told apart from the E in 0.00E+00 without more parsing.
  • Fractions of a second, which are rounded away, and negative serial numbers, which are rejected.
  • Writing dates back to .xlsx, and .ods or Apple Numbers files, which we have not tested here.
  • Other sheets than the first. Pick the sheet with data first, as shown in detecting the header row.
