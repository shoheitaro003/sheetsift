title: Handle merged cells in Excel imports with SheetJS description: SheetJS returns a merged cell's value only in its top-left cell. Tested JavaScript that fills merged rows, names two-row headers and flags the rest. date: 2026-11-23 ---

A customer uploads a sales report. "North" is merged over two rows, "Q1" over two columns, and the header takes two rows. Your importer reads it with sheet_to_json and gets columns called __EMPTY, a first record that is really the second header row, and a row where the region is empty.

By the end of this post you will have readMergedTable(bytes): seven functions plus a few one-line helpers, on top of SheetJS. It turns a two-row header into one name per column (Q1 Revenue), copies merged text labels down their column, skips title rows, and reports with Excel addresses the merges it should not guess about. Every function and every result quoted below is checked by our test file (the tests named mg:) in Node 22 with SheetJS 0.20.3.

What SheetJS gives you

A merged range keeps its value in its top-left cell only. The merge itself is stored separately, as a list of ranges, which SheetJS puts in sheet["!merges"]. Our test checks both on the report below, an .xlsx file written with openpyxl.

Three things go wrong. Columns under a group label have no name, so SheetJS calls them __EMPTY and __EMPTY_1. The second header row comes back as a record. And every row covered by a merge, except the first, is empty in the merged column.

The merges are all there in sheet["!merges"]; the code below uses them.

Step 1: read the rows and the merges

The code in steps 1 to 4 goes in one module: the small helpers at the top of step 2 are used by the later steps too.

One term first. A sheet's stored range is the block of cells the file says it uses, kept in sheet["!ref"], such as A1:F6. It does not have to start at A1. The code counts rows and columns from its first cell, called origin, and moves each merge by it so merges and rows use the same positions. Each merge keeps its original address, because that is what the user sees in Excel.

{{code:MG_READ}}

header: 1 returns each row as an array, so you decide what the column names are. defval: "" fills missing cells and blankrows: true keeps empty rows, so rows[r][c] always points at the same cell as the sheet.

raw: true returns the stored value instead of the text Excel displays. In an .xlsx file, a cell shown as 12% arrives as 0.12, and 1,234.50 as 1234.5. In a CSV it keeps text as text, so 0123 is not turned into 123.

CSV files are text, so readSheet decodes them itself: as UTF-16 when the file starts with a UTF-16 byte order mark (BOM), and as UTF-8 otherwise. A file that is not valid UTF-8, such as a Windows-1252 export with accented letters, or UTF-16 without a BOM, throws a TypeError; our post on decoding legacy CSV files shows how to read those.

Step 2: find the header rows and name the columns

The header has more than one row when a merge in it says so. A label merged down, like Region over rows 1 and 2, covers the row below. A label merged across, like Q1 over C and D, names a group, so the row below holds the real column names.

{{code:MG_HEADER}}

Why each rule is there:

  • A header row holds only text. A row with a number, a date or a boolean is data, so a merged header over data columns cannot swallow the first record. (With raw: true, dates in an .xlsx file arrive as serial numbers; our post on reading Excel dates shows how to convert them.)
  • A group needs a label under every column it covers. Q1 over Revenue and an empty cell is not a two-row header. If the row below is merged too, each column takes the value of the merge it sits in, so 2026 over a merged Q1 and a merged Q2 works.
  • The loop repeats because one extra row can bring in another: 2026 over Q1 and Q2, each over Rev and Cost, gives names like 2026 Q1 Rev.
  • maxDepth is 3 because a label merged down over many rows is more likely a layout choice than a header. Such a merge is reported in step 3.
  • A merge counts once per column. Region merged over two rows gives Region, not Region Region.

Two fills would change your numbers. An invoice total of 100 merged over two invoice lines, copied down, becomes 200 when you add up the lines. A note merged over C and D, copied across, would also land in D, which may be your amount column. In both cases the value stays in the cell where the file stores it, and the user decides. Dates count as numbers here, because with raw: true an .xlsx date arrives as a serial number; if a date column is grouped on purpose, fill it with fillDown from the CSV section below.

A file can still hold values in the other cells of a merge. Our test writes one with SheetJS: North merged over A2:A3, with South stored in A3. The merged range covers A3, so the user sees only North. fillMerges reports the hidden value and does not import it, for every shape of merge.

"The whole table width" means from the first column to the last column that has a name. A stray cell further right, such as a comment in column H, does not stop a footnote row from being recognised. A merge right of the last named column, such as a logo box, is ignored, and so is a merge below the last row of the sheet.

Step 4: read the table

readMergedTable puts the steps together and returns one record per data row, with the row number the user sees in Excel. Two helpers come first; readMergedTable itself runs four numbered steps: name the columns, fill or flag the merges, check the header, build the records. It throws if it cannot read the file: a TypeError for a text file that step 1 refuses, and a SheetJS error for a damaged .xlsx.

{{code:MG_TABLE}}

Besides the merges, it reports header problems that merges often cause:

  • A value under a header cell that is not merged, such as Ana under Name. In a real two-row header that cell is empty, so the lower row may be the first record.
  • A first data row with text in the same columns as the lower header row. This is the other sign that the lower row is data. It also flags some real headers over text-only data.
  • A column with data but no name. A column with neither is dropped without a message.
  • A name used twice. Email and EMAIL count as the same name. The second one is renamed Amount (2), so both values reach the preview instead of one overwriting the other.

Rows that are empty in the file are skipped, even inside a merged region, so a blank line does not become a record. If the first row of the stored range has no names at all, as in an empty file or a sheet with blank rows above the table, you get one problem that says so.

If the header is not in the first row, pass its index as headerTop. It counts from the first row of the stored range, starting at 0, not from Excel row 1. Our post on finding the header row finds that index. A title merged across the top, such as Sales export in A1:B1, is above the header and is ignored. To match the combined names to your own fields, use column mapping.

CSV files have no merges

A CSV stores no merges. In our test, SheetJS returns no merges for a CSV, and a region merged over several rows arrives as one value followed by empty cells, the same as cells nobody filled in. You cannot tell the two apart from the file, so do not fill down on your own. If the user says a column is grouped this way, fill that column:

{{code:MG_CSV}}

Use it after readMergedTable, which reads CSV files too. Three differences from .xlsx:

  • Every value in a CSV arrives as a string ("90", not 90), so convert numbers and dates in your own checks.
  • Title and footnote rows arrive as records. In our test, Note: figures in EUR becomes a record whose Region is the note, with no note or problem. Remove such rows before fillDown, or the note is copied into the rows below it.
  • If a file has sections, run fillDown on each section's records separately; otherwise a region carries over into the next section. The first rows stay empty if the column starts empty.

What this does not cover

  • Two-row headers in a CSV. Without merges you cannot see where Q1 ends, so readMergedTable reads one header row. Combine the rows yourself after the user confirms.
  • Numbers in a header row. A header cell typed as a number, such as the year 2026 under a merged Revenue, makes that row data, because a header row holds only text here. You get the columns Revenue and Revenue (2) with a repeated-name problem, and the years as the first record. If your users' files do this, type the years as text or confirm the header with the user.
  • A header over text-only data. Contact merged over two columns, with an email and a phone number stored as text below it, looks like a two-row header, so the first record becomes column names. So does Name merged over A1:A2 with City in B1 and Berlin in B2: you get the column City Berlin. The checks in step 4 report both files, but they are signs, not proof; that is why the user confirms the header.
  • A title merged down into the header. A merge that starts above headerTop and ends inside the header is not counted as a header row, but its value still becomes part of a column name. Pass the row under it as headerTop, or unmerge it.
  • Section labels as data. A row like Europe across the table is skipped. If the rows below belong to it, add it as a column yourself.
  • Other sheets and hidden rows. Only the first sheet is read, and this code does not check whether a row is hidden.
  • Blank cells that are not merged. They stay empty. Our post on placeholder values shows how to report them in required columns.
