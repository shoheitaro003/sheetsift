Your importer treats row 1 as the column names. The customer's file starts with Monthly sales, a date range and a blank line, so every field is mapped wrong, or the import fails with "column Email not found".

This post builds a header detector in five steps. At the end you have a function that returns the header row, whether it is sure, and why, plus code that turns the rows below it into records with the row numbers your user sees in Excel. Every function, and every result quoted below, is checked by our test file.

Why "the widest row of text" is not enough

Our post on why CSV importers break on real Excel files uses a short rule: take the widest row of unique text in the first 15 rows. It works for a title above the table. It fails on this file, which our tests check:

Row 3 has two columns named Date, so the uniqueness rule rejects it, and the short rule returns row 1. Nothing tells you it guessed. The version below picks row 3, and in the layouts it cannot decide, it says so.

The idea: column names sit above typed values

A header row has three properties that titles, notes and data rows rarely have together:

  • Fill: it spans most of the table's width. A title or a "Prepared by" line fills one or two cells.
  • Labels: its cells are words, not numbers, dates or emails.
  • Contrast: under its cells, the values change kind. MRR is a word; the cell under it is 49. This is the strongest signal, because a data row of text (a name, a city) has text under it too.

Each row in the first 20 gets a score from these three. The highest score wins, and three checks decide whether to trust it.

Step 1: label, value or empty

Every cell is put into one of three kinds. A label could be a column name. A value is data: a number, a date, a time, TRUE/FALSE or an email. (Not Yes/No: No is a common name for a row-number column.) Placeholders such as N/A, - and null, and Excel error values such as #DIV/0!, count as empty: they are neither data nor a name.

Typed cells are values at once: when you read an .xlsx file as shown in step 5, a cell that holds a number arrives as a JavaScript number, however Excel formats it. For text, a few patterns decide. (In JavaScript, \s also matches no-break spaces, so 1 234,56 with U+00A0 counts as a number.)

{{code:HDR_KIND}}

The patterns are deliberately loose, because they only need to separate "looks like data" from "looks like a name". 1.234,56 €, (1,234.56), 12%, 1e5, 08/11/2026, 2026-11-08T10:00:00Z, Nov 8, 2026 and 10:30 AM are values. E-mail, MRR ($), Q1 2026 and Prepared by: are labels.

Loose patterns misfile some cells. 090-1234-5678 and ID-0042 are labels, while +81 90 1234 5678 and 1.2.3.4 are values. The other columns usually decide. In our test, a Name, Phone, Plan, MRR table with two rows (Yui, 090-1234-5678, Pro, 49 and Ken, +81 90 1234 5678, Free, 0) still picks the header, but with sure: false: the more text columns a table has, the less evidence there is. (Reading the numbers correctly is a separate job, covered in our post on European number formats.)

Step 2: score each row

The input to everything below is an array of rows, each an array of cells, as any spreadsheet or CSV parser returns. To measure fill you need the table's width. The number of filled cells that appears in the most rows is a good estimate, because data rows usually outnumber everything else. When they do not (five one-cell notes above two data rows, say), contrast still decides: our tests include that file.

{{code:HDR_SCORE}}

Two filters run before any score: at least half the table's width must be filled, and at least three quarters of the filled cells must be labels. That removes titles, notes and most data rows. The "three quarters" leaves room for one odd header such as 2026 in a four-column table.

For contrast, the function looks up to three rows down for the first non-empty cell in each column, so a blank first data row does not hide the change. Contrast counts twice because it is the strongest evidence that a row names the columns under it. Key-value lines such as Period | 2026-01-01 also have a value under a label, but they never reach scoring: half their cells are values. Duplicate names cost a little, but do not disqualify the row: real headers repeat names, as in the example above.

Step 3: pick the best row and decide whether to trust it

A detector that always answers will sometimes be wrong without telling anyone. This one returns sure: false and a reason in three cases, and row: null when no row qualifies, so your import screen can ask the user instead. Missing rows (undefined entries some parsers leave) are treated as empty.

{{code:HDR_FIND}}

Read sure: true as "a row of labels above at least one typed column, with no close rival", not as proof. A table that is all text except one number column passes on that one column.

The last check looks at the row right above the winner. If it is all labels and either has gaps (group labels over merged cells) or is as wide as the winner, either row could be the header. That catches two-row headers and a bad first value, as in the Email example.

It also raises false alarms. A two-column table directly under key-value lines such as Owner | Ken (no blank line between) is always flagged, and so is Owner | (blank) | Ken above a wider table. In the layouts we tested, every wrong pick comes with sure: false, so the cost is a click, not a silent wrong import.

When sure is false, show the user the first 20 rows with the detected row highlighted and let them click the right one. When row is null, ask whether the file has a header at all.

Step 4: turn the rows below into records

Once you have the header, three details decide whether the records are usable: duplicate names, columns without a name, and the row numbers you show in error messages.

{{code:HDR_RECORDS}}
  • Duplicates get a suffix, compared without case: Amount, amount becomes Amount, amount (2). Without this, the second column silently overwrites the first in your object.
  • A column without a name is dropped if it is empty, and named after its Excel column letter, such as Column C, if it holds data.
  • Real names are kept first. Duplicates and generated names only take names no real column uses: for Amount, amount, Amount (2) the second column becomes amount (3), and the real Amount (2) keeps its name.
  • Records are built with Object.fromEntries, not by assigning keys. A header cell named __proto__ then becomes an ordinary key instead of changing the object's prototype.
  • A null header index gives no records, so you can pass found.row straight in and ask the user when it is empty.
  • Blank rows and repeated header rows are skipped. A short row is padded with "".
  • row is the number the user sees in Excel, so "row 7: invalid date" points at the right line even though rows were skipped.

Step 5: wire it to SheetJS

SheetJS (the xlsx package) reads a spreadsheet file into a worksheet object. sheet_to_json with header: 1 returns an array of rows, which is the input the functions above expect. Our test suite runs this function against SheetJS 0.20.3.

{{code:HDR_SHEETJS}}

Why each option is there:

  • raw: true with cellDates: true returns numbers as numbers and dates as Date objects, so step 1 does not have to guess from formatted text such as 1.234,00 €.
  • blankrows: true keeps empty rows in the array, so an array index still maps to one spreadsheet row.
  • origin fixes an offset that is easy to miss. The array starts at the top-left cell of the sheet's stored range (!ref), not at A1. Our test saves a sheet whose range starts at B3: the header on spreadsheet row 5 comes back at index 2. Without the offset, every row number in your error messages is off by two, and generated column letters are off by one.

Why not let sheet_to_json build the objects? You can, but its default names duplicate columns Date, Amount, Date_1, Amount_1 (also checked in our tests) and it does not skip repeated header rows. With toRecords you control both.

findHeader and toRecords do not depend on SheetJS. Any CSV parser that returns an array of rows works; its cells are usually all text, and step 1 then uses its patterns for every cell.

What this does not cover

  • Headers below row 20. Raise scan if your files have long cover notes.
  • Two-row headers. They are detected, not merged. If you need Q1 Revenue, combine the two rows yourself after the user confirms.
  • Headers that are numbers (years, months as 1 to 12). They return null; ask the user.
  • A units row under the header (kg, USD). It is picked as the header, with sure: false.
  • Values with units (5 kg, USD 5) count as labels, so tables of them give weak evidence.
  • A header narrower than the data, such as two names above five filled columns. The fill filter rejects it and you get null.
  • Value formats step 1 does not know, such as fractions (1/2) or dates in other languages. Add patterns for the files your users send.
  • Several tables on one sheet, or a table turned sideways (names in column A). Flagged or not found, never split.
  • Rows with more values than headers. Extra cells are ignored here. They often mean an unquoted comma in a CSV, which needs its own check.
