A customer in Germany uploads a CSV with a price column. The first value is 1.234,56. Your importer calls parseFloat, stores 1.234, and nobody notices until an invoice is off by a factor of a thousand.

{{code:EU_PROBLEM}}

JavaScript can format numbers for any locale with Intl.NumberFormat, but it has no matching parse function. This post builds one in about 70 lines, in five small steps. Every function runs in our test suite, so you can copy them as they are.

The separators in this table are the ones Intl.NumberFormat produces for en-US, en-GB, ja-JP, de-DE, it-IT, es-ES, nl-NL, pt-BR, fr-FR, de-CH and en-IN in Node.js. Our tests check each one, because these outputs come from the ICU library and can change between versions.

Negative numbers add more variants: -1.234,56, the Unicode minus sign − (U+2212), accounting brackets (1,234.56), and a minus at the end, 1.234,56-. The last one comes from financial systems; Excel does not recognise 150- as a negative number either (ASAP Utilities, 2007, updated 2021).

Step 1: separate the sign and remove the noise

First remove everything that is not part of the number: spaces of every kind, apostrophes used as thousands separators, currency symbols and three-letter codes like EUR. Then read the sign, wherever it is. The function returns the sign and a "body" that contains only digits, dots and commas, or null if the cell is not a number at all.

{{code:EU_SPLIT}}

Removing all spaces is safe because none of these formats uses a space as the decimal separator. The currency code is only removed when it sits right next to the number, so a cell like 12abc34 is rejected instead of becoming 1234.

Step 2: turn the body into a number, strictly

Once you know which character is the decimal separator, the other one must be a thousands separator. That is a strong rule, and you should enforce it: groups have three digits (or two, then three, for Indian lakh grouping), there is at most one decimal separator, and no thousands separator after it. Anything else is rejected.

{{code:EU_TONUMBER}}

The strictness is the point. With a comma as decimal separator, 1.23 is not a valid number, so it returns null rather than 123. A rejected cell can be shown to the user. A wrong number goes straight into your database.

Step 3: when you know the locale

If the user has told you their locale (an account setting, or a choice on the import screen), ask Intl.NumberFormat which separators that locale uses. formatToParts splits a formatted number into labelled pieces, including group and decimal.

{{code:EU_LOCALE}}

parseLocaleNumber("1.234,56", "de-DE") returns 1234.56, and the same string with "en-US" returns null. Our test also formats -1234567.891 in eleven locales and checks that parsing gives the same number back.

Be careful with navigator.language. It tells you how the browser is set up, not where the file came from. An accountant in London can easily upload an export from the German office.

Step 4: when you don't know the locale, look at the whole column

One value can be ambiguous; a column usually is not. 1,234 could be one thousand two hundred thirty-four or one point two three four. But if the same column also contains 12,5 or 1.234,56, the answer is clear. Each value casts a vote, and the column gets a format only if all votes agree.

{{code:EU_DETECT}}

The rules per value:

  • Both a dot and a comma: the last one is the decimal separator.
  • The same separator twice (1.234.567): it is a thousands separator.
  • One separator not followed by exactly three digits (12,5, 99,90): it is the decimal separator.
  • One separator after a leading zero (0,125): decimal, because nobody writes a thousands separator after a zero.
  • Exactly three digits after a single separator (1,234): no vote. This is the case that cannot be decided from the value.

If the votes contradict each other, the function returns null too. A column with both 1.234,56 and 1,234.56 was probably pasted together from two sources, and someone needs to look at it.

Step 5: put it together for an import

Detect from the data first. Use the locale the user chose only when the data gives no evidence. If neither is available, don't pick a default: show the column and ask.

{{code:EU_COLUMN}}

For a German export with 1.234,56, -99,90 €, 1.000-, an empty cell and n/a, this returns [1234.56, -99.9, -1000, null, null]. The two null cells are the ones to highlight in your preview. A column with only 1,234 and 5,678 returns no format at all until the user picks one.

What this does not cover

  • Numbers that are already numbers. Cells that a spreadsheet stored as real numbers don't have this problem. It is text that does: CSV files, and numbers typed into a cell as text.
  • Scientific notation such as 1,5E+03. Add it only if your users' files contain it.
  • Arabic, Persian or Devanagari digits. These need a digit mapping step before step 1.
  • Percentages. Strip % in step 1 and divide by 100 afterwards, but only for columns you know are percentages.
