title: Remove invisible characters from CSV and Excel cells in JS description: Zero width spaces, no-break spaces and BOMs make equal values unequal. Tested JavaScript that finds, cleans and reports them per cell before import. date: 2026-11-18 ---

A customer imports a file, and your app says ana@example.com is not in the system, or adds her twice. The value looks right, but it holds a character you cannot see, such as a zero width space at the end. trim() does not remove that one, so the lookup and the duplicate check both compare different strings.

By the end of this post you will have cleanCell(value, kind) and cleanRows(rows), about 100 lines with no dependencies. They remove or replace hidden characters, treat IDs (emails, SKUs) more strictly than free text (names, notes), and report every hidden character they remove or replace, and every ID that NFKC normalization changes, with its row, so your import preview can show what was changed instead of doing it silently. Every function, and every result quoted below, is checked by our test file in Node 22.

Why trim() is not enough

This block only shows the problem. In the code, hidden characters are written as escapes such as \u200B so you can see them; in a real file they are the characters themselves.

{{code:INV_PROBLEM}}

trim() removes only some characters, and only at the two ends. The no-break space (U+00A0) is one of them. The zero width space (U+200B) is not, and neither are the soft hyphen (U+00AD) or the word joiner (U+2060). /\s/ does not help: our test checks every character from U+0000 to U+FFFF and finds that \s matches exactly the characters trim() removes.

Step 1: find the characters you cannot see

Every Unicode character has a general category, a short code for what kind of character it is. This post treats three categories as hidden: Cc (control characters such as tab and line feed), Cf (format characters such as the zero width space and the byte order mark) and Z (separators: all kinds of spaces, plus the line and paragraph separators). Three blank characters are in other categories, so HIDDEN lists them by code: U+2800 (braille pattern blank, a symbol, So), U+3164 (hangul filler, a letter, Lo) and U+FFA0 (its half-width form, also Lo). A regular expression with the u flag can match a category with \p{...}, so you do not need to list every character. (Our tests check every category this post names with these same regular expressions in Node 22, and the character names against Python's unicodedata module.)

{{code:INV_FIND}}

NAMES only gives readable names for the characters this post discusses; any other match is still found and reported as "invisible character" with its code, such as U+202E. showHidden is for logs and support tickets: showHidden("ana@example.com\u200B") returns ana@example.com<U+200B>.

Step 2: clean a cell by kind

The right fix depends on what the column holds, so cleanCell takes a kind. Use "id" for values that are compared or looked up and never contain spaces: emails, SKUs, customer numbers. Use "text" for values people read: names, addresses, notes.

{{code:INV_CLEAN}}

Each rule, and why:

  • Spaces of every width become a plain space, and tabs too. A no-break space between two words in a name is meant as a space, so it is replaced rather than removed.
  • Line ends become \n. That includes the vertical tab, form feed and next line controls (U+000B, U+000C, U+0085), so words on either side are not joined. A Windows line end (\r\n) inside a note is kept as one line break and not reported, since it is not a problem. A lone \r and the Unicode line and paragraph separators become \n and are reported.
  • Format and control characters are removed: zero width spaces, byte order marks, soft hyphens, and also control characters such as U+0007 that no cell should hold.
  • Text keeps joiners, direction marks and tag characters. The zero width joiner (U+200D) holds emoji sequences together: our test segments a family emoji, written as man, joiner, woman, joiner, girl (U+1F468 U+200D U+1F469 U+200D U+1F467), with Intl.Segmenter and gets one character with the joiners and three without them. The zero width non-joiner and the left-to-right and right-to-left marks (U+200C, U+200E, U+200F) are kept for the same reason: they are invisible on purpose, and a name or note may have been written with them. So are the tag characters (U+E0020 to U+E007F): some flag emoji are built from them, and our test shows a black flag (U+1F3F4) followed by six tag characters staying one character only while they are kept. In an ID none of these belongs, so they are removed.
  • IDs are normalized with NFKC. NFKC is the Unicode compatibility form: it turns full-width letters and digits into ASCII, so ＡＢ－１２３ becomes AB-123. It also turns ① into 1, x² into x2 and the ligature ﬁ into fi. That is what you want for an ID, but it changes what a note says, so text is not normalized. It does not turn every digit into ASCII: Arabic-Indic digits such as ١٢ stay as they are. When NFKC changes an ID, cleanCell records one change with code "NFKC" and the new value.
  • An ID with a space or line break inside is an error, not something to fix. ana @example.com (with a no-break space) could be a typo or two values in one cell; the user should decide. An ID that held nothing but hidden characters is an error too, "contains only invisible characters", since it would otherwise arrive as an empty value without warning. A few characters only become a space through NFKC, such as the acute accent ´ (U+00B4); those get their own message, "contains a character that NFKC turns into a space".

Positions count code points from 0 (the [...string] spread splits a string into code points), so an emoji earlier in the value counts as one position, not two. NFKC runs after the hidden characters are handled, so the positions always refer to the original value. Plain spaces at the ends are trimmed without a note. A hidden space at an end gets a note that it became a space, and is then trimmed with the rest.

cleanCell expects a string. It turns anything else into one with String(), which is fine for numbers but not for dates, so turn date cells into text first, as in our post on reading Excel dates.

NFKC does not make every dash the same. The hyphen U+2010 stays U+2010, so AB‐123 written with it still differs from AB-123. If your IDs have a fixed format, check it after cleaning (for example with a regular expression) and reject values that do not fit.

Step 3: report the changes and find duplicates

cleanRows runs cleanCell on each column with the kind you set for it, collects notes (changes the user can review) and errors (values that must be fixed before import), and finds repeated emails after cleaning. Columns that are not in COLUMN_KINDS are copied unchanged, a configured column missing from a row comes back as "", and describe counts positions from 1 for people.

The duplicate is found only because the zero width space was removed first. Show the notes in your import preview so the user knows what changed; block the import, or skip the row, while there are errors.

Clean after parsing, not before. In our test, SheetJS 0.20.3 returns the zero width space and the no-break space unchanged from both an .xlsx and a CSV file, so the cleaning step is still needed after XLSX.read. Header names need different rules (case, plurals, punctuation); our post on mapping columns to your fields covers them. If your CSV parser keeps a byte order mark at the start of the file, it ends up in the first header name, so strip a leading U+FEFF there too.

What this does not cover

  • Lookalike letters. The Cyrillic а (U+0430) is visible and looks like the Latin a; it is not a hidden character, so cleanCell keeps it. Rejecting non-ASCII characters in IDs is a separate check.
  • Other direction controls. The embedding, override and isolate characters (U+202A to U+202E and U+2066 to U+2069, all in category Cf) are removed from text too. If you import right-to-left text such as Arabic or Hebrew, test with real samples from your users and add these to KEEP_IN_TEXT if they need them.
  • Variation selectors and combining marks, such as U+FE0F (variation selector-16) or U+0301 (the combining acute accent in a decomposed é). They are in category Mn, not in the three hidden categories, so they are kept, and two spellings of é still compare as different strings. Add normalize("NFC") to text if you compare names.
  • Everything else an ID may hold. Variation selectors, private-use characters (U+E000 to U+F8FF) and broken surrogate pairs pass through cleanCell. After cleaning, check each ID against the characters its format allows, for example /^[\x21-\x7E]+$/ for printable ASCII.
  • Numbers. A no-break space used as a thousands separator becomes a plain space, so 1 234,5 is still not a number. Parse number columns with their own rules, as in our post on European number formats.
  • Case. Ana@Example.com and ana@example.com stay different; lowercase the key in cleanRows if your app treats them as one.
