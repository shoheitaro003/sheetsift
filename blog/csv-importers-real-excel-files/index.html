Why CSV importers break on real Excel files, and how to fix each case in JavaScript

2026-11-05

Most import screens are built and tested with a CSV that someone exported from a database five minutes earlier. Headers on row 1, ISO dates, dots for decimals, UTF-8. Then the first real customer uploads customer_export_FINAL(2).xlsx and the import either fails or, worse, succeeds with the wrong numbers.

This post walks through the six differences that cause most of those failures, with a small JavaScript function for each. Every code example on this page runs in our test suite, so you can copy them as they are.

1. The header row is not row 1

Exports from accounting tools, banks and Excel power users usually start with a title, a date range or a blank line. If your importer treats row 1 as the header, every column name is wrong.

A reliable rule: scan the first rows and pick the one with the most cells that look like labels. Labels are not numbers, not dates and not email addresses, and they don't repeat.

function findHeaderRow(rows, scan = 15) {
  let best = 0, bestCount = 0;
  for (let i = 0; i < Math.min(rows.length, scan); i++) {
    const cells = rows[i].map((c) => String(c ?? "").trim()).filter(Boolean);
    if (cells.length < 2) continue;
    const labels = cells.every((c) => !/^[\d\s.,\-\/:$€£¥%]+$/.test(c) && !c.includes("@"));
    const unique = new Set(cells.map((c) => c.toLowerCase())).size === cells.length;
    if (labels && unique && cells.length > bestCount) {
      best = i;
      bestCount = cells.length;
    }
  }
  return best; // 0-based index of the header row
}

For a file whose first rows are Export (do not edit), a blank line, then Name, Email, Plan, this returns 2. Show the detected row to the user and let them change it. Detection is a suggestion, not a decision.

2. A totals row at the bottom

People add a Total row before exporting. If it reaches your database, you have a customer called "Total" with a revenue figure equal to everyone else combined.

const TOTAL = /^(grand\s+)?(sub-?)?totals?\b|^(sum|summe|gesamt)\b|^(合計|小計|総計)/i;

function isTotalsRow(row) {
  const first = row.map((c) => String(c ?? "").trim()).find(Boolean) ?? "";
  return TOTAL.test(first);
}

Note the word boundary in the pattern: Totally Fit Ltd is a customer, not a totals row. Add the words your users actually write. The pattern above covers English, German and Japanese.

3. Dates that can be read two ways

04/05/2026 is 4 May in most of the world and 5 April in the United States. No single value can tell you which. The column can: if any value in it has a first number above 12, the column is day-first. If any has a second number above 12, it is month-first.

function dateOrder(values) {
  let dayFirst = false, monthFirst = false;
  for (const v of values) {
    const m = /^(\d{1,2})[\/-](\d{1,2})[\/-](\d{4})$/.exec(String(v).trim());
    if (!m) continue;
    if (+m[1] > 12) dayFirst = true;   // 31/01/2026
    if (+m[2] > 12) monthFirst = true; // 01/31/2026
  }
  if (dayFirst === monthFirst) return null; // no evidence, or contradictory: ask the user
  return dayFirst ? "dmy" : "mdy";
}

When the function returns null, don't guess. Leave those cells unconverted and ask the user to confirm the format once for the whole column. A wrong date that looks valid is much harder to find later than a cell flagged for review.

4. Decimal commas

A German or French export writes one thousand two hundred and thirty-four euros fifty as 1.234,50. Parse that with parseFloat and you get 1.234. Decide the convention per column, then parse every value the same way.

const usesDecimalComma = (values) =>
  values.some((v) => /^-?\d{1,3}(\.\d{3})*,\d{1,2}$/.test(String(v).trim()));

function parseAmount(raw, decimalComma) {
  let t = String(raw).trim().replace(/[\s\u00a0]/g, "").replace(/^[$€£¥]|[$€£¥円]$/g, "");
  t = decimalComma ? t.replace(/\./g, "").replace(",", ".") : t.replace(/,/g, "");
  return /^-?\d+(\.\d+)?$/.test(t) ? Number(t) : null;
}

usesDecimalComma only returns true when it sees an unambiguous value such as 49,00 or 1.234,50. A column that contains only 1,234 stays in the default convention, because that value is valid both ways.

5. Excel files are not CSV files

If you accept .xlsx, three details matter.

  • Dates. Excel stores dates as numbers. Ask the parser for formatted text, and set the date format when you read the workbook. Setting it only when you convert the sheet gives you 4/3/26.
  • Empty first sheets. Workbooks often open with a cover or notes sheet. Use the first sheet that has data.
  • The library version. The xlsx package on the npm registry is stuck at 0.18.5, which is affected by a prototype pollution issue (CVE-2023-30533, fixed in 0.19.3) and a ReDoS issue (CVE-2024-22363, fixed in 0.20.2). SheetJS publishes current releases on its own CDN.
// npm install https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz
import * as XLSX from "xlsx";

async function readWorkbook(file) {
  // dateNF must be set here: setting it only in sheet_to_json gives "4/3/26".
  const wb = XLSX.read(await file.arrayBuffer(), { cellDates: true, dateNF: "yyyy-mm-dd" });
  const hasData = (name) =>
    XLSX.utils.sheet_to_json(wb.Sheets[name], { header: 1, defval: "" })
      .some((row) => row.join("").trim());
  const name = wb.SheetNames.find(hasData) ?? wb.SheetNames[0];
  return XLSX.utils.sheet_to_json(wb.Sheets[name], {
    header: 1, raw: false, defval: "", dateNF: "yyyy-mm-dd",
  });
}

6. Text encodings

CSV files from older Windows software are often not UTF-8. Reading them as UTF-8 turns Café into Caf�. Check for a byte order mark first, then try strict UTF-8, and fall back to the legacy encoding your users are most likely to have.

async function readText(file) {
  const buf = await file.arrayBuffer();
  const b = new Uint8Array(buf);
  if (b[0] === 0xff && b[1] === 0xfe) return new TextDecoder("utf-16le").decode(buf);
  if (b[0] === 0xfe && b[1] === 0xff) return new TextDecoder("utf-16be").decode(buf);
  try {
    return new TextDecoder("utf-8", { fatal: true }).decode(buf);
  } catch {
    // Not valid UTF-8. Pick the legacy encoding your users are most likely to have:
    // "windows-1252" for Western Europe and the Americas, "shift_jis" for Japan.
    return new TextDecoder("windows-1252").decode(buf);
  }
}

The rule behind all six: don't guess silently

Every case above has an input that cannot be resolved automatically: a file with two plausible header rows, a date column with no value above 12, a number like 1,234. An importer earns trust by converting what it can prove, and by showing the rest to the person who knows the data. A cell marked "needs a decision" costs your user five seconds. A silently wrong date can cost a support ticket, or a customer.
