Parse a large CSV file in the browser without freezing the page

2026-11-16

A user picks an 11 MB CSV export and your import screen calls file.text() and parses it. In our Chromium test the page could not run anything else for about 400 ms, on a fast machine; a slower device or a bigger file makes the pause longer. The whole file also sits in memory twice, as one string and as an array of rows. With a quick split("\n") parser, the rows can be wrong as well.

By the end of this post you will have importCsv(file, { onBatch }): three small ES modules with no dependencies. It reads the file as a stream inside a Web Worker and hands your page rows in batches, each row with its line number, plus a list of problems, progress and cancel. Every result quoted below is checked by our test file in Node 22, and the browser results by a Chromium test.

Why the page stalls, and why split() is not enough

Your page's JavaScript runs one task at a time on the page's main thread. A parser called there keeps the thread until it returns, so your progress bar update and your Cancel button handler wait for it. Our test measures this with setInterval set to 5 ms while a 100,000-row file (11 MB, 8 columns) is parsed on the page: the longest gap between ticks is the pause, 381 to 431 ms in three of our runs.

The quick parser many importers start with has a second problem. A cell in quotes can contain commas and line breaks, and splitting on them cuts it apart:

const csv = 'id,note\n1,"Line one\nline two"\n2,"Acme, Inc"\n';
const rows = csv.trim().split("\n").map((line) => line.split(","));
rows.length; // 4
rows[1].length; // 2
rows[3].length; // 3

The file has two records, but splitting gives four rows, and "Acme, Inc" becomes two cells. So the fix has three parts: a parser that understands quotes and accepts the text in pieces (step 1), a reader that feeds it the file piece by piece (step 2), and a Web Worker, a script that runs on its own thread next to the page, so the parsing leaves the main thread (steps 3 and 4).

If you would rather use a library: the README of Papa Parse 5.7.1 on npm (read on 2026-11-16) lists streaming large files, worker threads to keep the page reactive, and pause, resume and abort. This post is for when you want the code in your own repository, and it shows the pieces a SaaS import needs around the parser: the worker waits for your saving code, every row carries its line number, and invalid bytes are an error. What you give up: the same README lists delimiter detection and header row support, and a maintained library gets fixes you would otherwise write yourself.

Step 1: a parser that accepts chunks

A stream delivers the text in chunks, and a chunk can end anywhere: inside a quoted cell, between the two quotes of "" (an escaped quote inside a quoted cell), or between the \r and \n of a Windows line end. So the parser cannot look ahead. It keeps its state in a few variables between calls and handles each character the moment it arrives. Put it in csv-stream.js:

// csv-stream.js
// Splits CSV text into rows. The text can arrive in chunks that end anywhere:
// inside a quoted cell, between the two quotes of "", or between \r and \n.
export function createCsvParser(options) {
  const { delimiter = ",", maxCellLength = 1000000, onRow } = options;
  const onError = options.onError ?? (() => {});
  if (delimiter.length !== 1 || "\"\r\n".includes(delimiter)) {
    throw new Error(`delimiter must be one character, not a quote or line break`);
  }
  let cell = "", row = [];
  let inQuotes = false;     // inside "..."
  let afterQuote = false;   // just read a closing quote, or the first quote of ""
  let cellQuoted = false;   // the current cell started with a quote
  let rowQuoted = false;    // some cell in this row started with a quote
  let afterCR = false;      // the last character was \r (as in a Windows \r\n)
  let line = 1, rowLine = 1, started = false;

  function endCell() {
    row.push(cell);
    cell = "";
    afterQuote = cellQuoted = false;
  }
  function endRow() {
    endCell();
    // An empty line is skipped. A line with only "" is a row with one empty cell.
    if (row.length > 1 || row[0] !== "" || rowQuoted) onRow(row, rowLine);
    row = [];
    rowQuoted = false;
  }

  function push(text) {
    if (!started && text) {
      if (text[0] === "\uFEFF") text = text.slice(1); // byte order mark
      started = true;
    }
    for (const ch of text) {
      const secondHalfOfCRLF = afterCR && ch === "\n";
      afterCR = ch === "\r";
      if (inQuotes) {
        if (ch === '"') {
          inQuotes = false;
          afterQuote = true;
        } else {
          cell += ch; // line breaks inside quotes belong to the cell
          if (ch === "\r" || (ch === "\n" && !secondHalfOfCRLF)) line++;
        }
      } else if (secondHalfOfCRLF) {
        // The row already ended at the \r.
      } else if (ch === '"' && afterQuote) {
        cell += '"'; // "" inside a quoted cell is one quote
        inQuotes = true;
        afterQuote = false;
      } else if (ch === delimiter) {
        endCell();
      } else if (ch === "\r" || ch === "\n") {
        endRow();
        rowLine = ++line;
      } else if (ch === '"' && cell === "" && !cellQuoted) {
        inQuotes = cellQuoted = rowQuoted = true;
      } else {
        if (afterQuote) {
          const message = `text after a closing quote: ${JSON.stringify(ch)}`;
          onError({ line, message });
          afterQuote = false;
        }
        cell += ch; // includes a quote in the middle of a cell, as in 5" screen
      }
      if (cell.length > maxCellLength) {
        // Usually a quote that is never closed: stop, do not read on.
        const limit = `${maxCellLength} characters`;
        throw new Error(`line ${rowLine}: a cell is longer than ${limit}`);
      }
    }
  }

  function end() {
    if (inQuotes) {
      const message = "a quote opened on this line is never closed";
      onError({ line: rowLine, message });
    }
    if (row.length > 0 || cell !== "" || cellQuoted) endRow();
  }

  return { push, end };
}

afterQuote is what makes chunk boundaries safe. After a quote inside a quoted cell, the parser does not yet know whether the cell ended or an escaped quote started, so it waits for the next character, even if that arrives in the next chunk. afterCR does the same for \r\n. The test feeds the same tricky text in every possible two-way split, in more than 1,000 three-way splits and one character at a time, and checks that the rows are always identical.

line counts physical lines, so a row's line number is where it starts in the file, even when earlier cells contain line breaks. That is the number a user needs to find a bad row in a text editor.

The parser keeps reading after a problem and reports it through onError, so one bad row does not hide the others. Here is what it does with the cases our tests cover:

The unclosed quote matters most in large files. One stray quote at the start of a cell turns everything after it into a single cell, so without a limit the parser would read the rest of the file into one string. maxCellLength (one million characters by default) stops the import as soon as a cell grows past it, with the line where the cell started. Set it to the longest value your fields can hold.

Step 2: read the file as a stream

file.stream() reads the file in chunks of bytes, so the whole file never has to be in memory as one string. TextDecoderStream turns the bytes into text and keeps a character whose bytes are split between two chunks for the next one; the test cuts a file at every byte, including inside 山 and inside the byte order mark, and gets the same rows each time. A TransformStream in between counts bytes for the progress bar. Add this to csv-stream.js:

const PIECE = 65536; // characters parsed at a time, however big the chunk

// Reads a File (or Blob) as a stream and yields parsed rows in batches.
export async function* csvBatches(file, options = {}) {
  const { batchSize = 2000, encoding = "utf-8", ...parserOptions } = options;
  if (!Number.isInteger(batchSize) || batchSize < 1) {
    throw new Error("batchSize must be a whole number of at least 1");
  }
  let rows = [], errors = [], bytesRead = 0;
  const full = []; // batches of exactly batchSize rows, waiting to be yielded
  const parser = createCsvParser({
    ...parserOptions,
    onRow(cells, line) {
      rows.push({ line, cells });
      if (rows.length === batchSize) {
        full.push({ rows, errors });
        rows = [];
        errors = [];
      }
    },
    onError: (error) => errors.push(error),
  });
  const countBytes = new TransformStream({
    transform(chunk, controller) {
      bytesRead += chunk.byteLength;
      controller.enqueue(chunk);
    },
  });
  // fatal: true turns bytes that are not valid in `encoding` into an error.
  const reader = file.stream().pipeThrough(countBytes)
    .pipeThrough(new TextDecoderStream(encoding, { fatal: true })).getReader();
  try {
    for (;;) {
      const { value, done } = await reader.read();
      if (done) {
        parser.end();
        while (full.length) yield { ...full.shift(), bytesRead, done: false };
        yield { rows, errors, bytesRead, done: true }; // may have no rows
        return;
      }
      for (let i = 0; i < value.length; i += PIECE) {
        parser.push(value.slice(i, i + PIECE));
        while (full.length) yield { ...full.shift(), bytesRead, done: false };
      }
    }
  } finally {
    // Runs on errors and when the caller stops early (break): release the file.
    reader.cancel().catch(() => {});
  }
}

The generator yields batches of exactly batchSize rows, then a last batch, possibly empty, with done: true. Each row is { line, cells }, and the first one is your header row. A problem comes in the batch that was being filled when it was found, with its line number; an unclosed quote is only known at the end, so it comes in the last batch.

If the loop stops early, because of an error or because your code leaves the for await loop, finally cancels the reader and releases the file. A batchSize that is not a whole number of at least 1 is refused, since it would put the whole file in one batch.

Chunk sizes differ a lot between runtimes: in our tests, Chromium 153 delivered the 11 MB file in chunks of up to 2 MiB, and Node 22 delivered it as one chunk. That is why the loop parses 65,536 characters at a time. It is also why bytesRead is a share of the file read, not parsed: it can run ahead of the rows by one chunk, so treat it as a rough progress bar.

fatal: true makes bytes that are not valid in the chosen encoding throw a TypeError. Without it, a Windows-1252 file turns every é into � without any error. For files in older encodings, pass the right label as encoding, such as "shift_jis"; our post on reading Shift_JIS, Windows-1252 and UTF-16 CSV files shows how to detect it. TextDecoderStream already removes a UTF-8 byte order mark; the parser removes one too, for text that comes from somewhere else.

Step 3: move the work into a worker

The worker is a module worker, so it can import csvBatches instead of keeping a second copy of it:

// csv-worker.js
import { csvBatches } from "./csv-stream.js";

let continueReading = null;

self.onmessage = async ({ data }) => {
  if (data.type === "next") return continueReading?.();
  try {
    let rowCount = 0;
    for await (const batch of csvBatches(data.file, data.options)) {
      rowCount += batch.rows.length;
      // Wait until the page has handled this batch, so unread rows never pile up.
      const handled = new Promise((resolve) => (continueReading = resolve));
      self.postMessage({ type: "batch", ...batch, rowCount });
      await handled;
    }
  } catch (error) {
    const message = String(error?.message ?? error);
    self.postMessage({ type: "failed", message });
  }
};

The worker waits for the page to say "next" before it reads further. Without that, it parses as fast as it can and sends every batch at once. If your page saves each batch to an API more slowly than the worker parses, all 100,000 rows then pile up in memory waiting to be saved, which is what streaming was meant to avoid. With the wait, at most one batch is in flight; the test checks that the worker never gets more than one batch ahead.

Step 4: the page side

// import-csv.js
// Parses a CSV file in a worker. onBatch(rows, errors, signal) may be async:
// the worker waits for it before sending more, and signal aborts on cancel().
// options (batchSize, encoding, delimiter, maxCellLength) must be plain data.
export function importCsv(file, { onBatch, onProgress, options = {} }) {
  let worker = new Worker(new URL("./csv-worker.js", import.meta.url), {
    type: "module",
  });
  const aborter = new AbortController();
  let resolveResult, rejectResult;
  const result = new Promise((resolve, reject) => {
    resolveResult = resolve;
    rejectResult = reject;
  });
  // Each returns false when the import had already ended.
  const stop = () => {
    if (!worker) return false;
    worker.terminate();
    worker = null;
    return true;
  };
  const finish = (value) => stop() && (resolveResult(value), true);
  const fail = (error) => stop() && (rejectResult(error), true);

  worker.onmessage = async ({ data }) => {
    if (!worker) return; // cancelled while this message was waiting
    if (data.type === "failed") return fail(new Error(data.message));
    try {
      await onBatch(data.rows, data.errors, aborter.signal);
      if (!worker) return; // cancelled while onBatch was running
      onProgress?.(file.size ? data.bytesRead / file.size : 1);
      if (data.done) finish({ rowCount: data.rowCount });
      else worker.postMessage({ type: "next" });
    } catch (error) {
      fail(error); // from onBatch or onProgress: stop instead of hanging
    }
  };
  worker.onerror = (event) => {
    fail(new Error(event.message || "the CSV worker failed"));
  };
  worker.onmessageerror = () => fail(new Error("a batch could not be received"));
  try {
    worker.postMessage({ type: "start", file, options });
  } catch (error) {
    fail(error); // for example a function in options, which cannot be sent
  }

  const cancel = () => {
    if (fail(new DOMException("Import cancelled", "AbortError"))) aborter.abort();
  };
  return { result, cancel };
}

importCsv returns { result, cancel }. result resolves with { rowCount }, header included, after the last batch. It rejects when the worker fails, when bytes are not valid in the chosen encoding, when a cell passes maxCellLength, when your onBatch or onProgress throws, or when options contains something that cannot be sent to a worker, such as a function. Every failure ends the import instead of leaving it waiting, and the tests cover each one. Always await or catch result, also after cancel(), or the rejection goes unhandled.

cancel() stops the worker, rejects result with an AbortError and aborts the signal passed to onBatch, so you can pass it to fetch and stop a save in flight. The tests check that no batch and no progress call arrive after a cancel, even when it happens while onBatch is still saving, and that a cancel after the end changes nothing.

import.meta.url means the file with importCsv must itself be an ES module, and csv-worker.js and csv-stream.js must be served next to it. Our test runs the three files unbundled, as module scripts in Chromium 153. We have not tested a bundler: if you use one, check in its documentation which form of new Worker(...) it recognizes and whether it bundles the worker's imports.

Using it in an upload form

An import can fail at row 80,000, after tens of thousands of rows have already been sent to your API. So save batches to a staging area under an import id, and only make them live after the last batch and after checking the problems. saveRows, commitImport and discardImport are your code. A save that was already on its way can still reach your server after the discard, so the server should refuse saves for an import id it has discarded.

import { importCsv } from "./import-csv.js";

const MAX_PROBLEMS = 100; // a wrong delimiter makes every row a problem
const input = document.querySelector("#csv-file");
const status = document.querySelector("#import-status");
const cancelButton = document.querySelector("#cancel-import");
let current = null;

input.addEventListener("change", async () => {
  const file = input.files[0];
  input.value = ""; // so that choosing the same file again fires "change"
  if (!file) return;
  current?.cancel(); // a new file replaces an import that is still running
  const importId = crypto.randomUUID();
  const problems = [];
  let header = null;
  const show = (text) => {
    if (current === job) status.textContent = text;
  };
  const job = importCsv(file, {
    async onBatch(rows, errors, signal) {
      problems.push(...errors);
      const records = [];
      for (const row of rows) {
        if (!header) {
          header = row.cells; // the first row is the header, not a record
          continue;
        }
        if (row.cells.length !== header.length) {
          const message = `${row.cells.length} cells, header has ${header.length}`;
          problems.push({ line: row.line, message });
        }
        records.push(row);
      }
      if (problems.length > MAX_PROBLEMS) throw new Error("too many problems");
      await saveRows(importId, header, records, signal); // yours: stage, not live
    },
    onProgress: (share) => show(`${Math.round(share * 100)}% read`),
  });
  current = job;
  cancelButton.onclick = job.cancel;
  try {
    const { rowCount } = await job.result;
    if (problems.length) throw new Error("problems");
    await commitImport(importId); // yours: make the staged rows live
    show(`Imported ${Math.max(rowCount - 1, 0)} rows`);
  } catch (error) {
    // yours: delete the staged rows (your server should also refuse late saves)
    await discardImport(importId).catch(() => {});
    if (error.name === "AbortError") return show("Import cancelled");
    const first = problems[0];
    show(first
      ? `${problems.length} problems; line ${first.line}: ${first.message}`
      : `Import failed: ${error.message}`);
  }
});

The first row is kept as header and not saved as a record. The loop also catches rows with a different number of cells from the header, which is how an unquoted comma usually shows up, as in Acme, Inc without quotes. A wrong delimiter makes every row a problem, so the import stops once there are more than MAX_PROBLEMS, before saving anything more. Choosing a new file cancels a running import, and the cancelled import cannot overwrite the new status.

The progress bar moves after each batch is saved, so it shows how far the import has got, not only the reading. The test runs this code with a 5,000-row file, a ragged row, a parser problem, a wrong delimiter, invalid bytes with a failing discard, a cancel and two files chosen one after the other.

You could also run csvBatches on the page and wait for a timer between pieces. The page would still parse every character itself, though; with a worker, it only receives finished batches.

What our Chromium test shows

The test builds the 100,000-row, 11 MB file in the page, with a quoted comma, an escaped quote, a line break and Japanese text in every row. In those three runs, parsing on the page took 381 to 431 ms in one piece, so the pause was that long. Through the worker the longest pause was 30 to 36 ms, and all 100,001 rows (header included) arrived in 51 batches, with the last row on line 200,000.

The worker is slower overall: 577 to 730 ms from start to the last batch, because each batch is copied to the page and the worker waits for the page before reading on. That is the trade: the page stays usable, and the import takes longer. The remaining pauses come from receiving the batches, so a bigger batchSize means fewer but longer pauses; measure with your own rows.

These are numbers from the machine that ran our tests, not a benchmark. The test itself only checks that the pause with the worker is shorter than without it and under 100 ms, that every row arrives with the right line number, and that cancel stops the worker.

What this does not cover

  • Excel files. They are not text, so this parser cannot read them. Our post on reading Excel dates with SheetJS shows one way to read them.
  • Guessing the delimiter or the encoding. You pass both. Read the first piece of the file with file.slice(0, 65536) if you want to guess them before starting. A first line such as sep=; is read as an ordinary row.
  • Finding the header row and mapping columns. Our posts on detecting the header row and mapping columns to your fields cover these; run them on the first batch.
  • Memory on your side. If onBatch pushes every row into one array, the whole file ends up in memory anyway. Save or process each batch, then let it go.
  • Very long rows. maxCellLength limits one cell, not a row; a file with a wrong delimiter setting and no line breaks can still build one huge row.
  • Unquoted commas in rows of the right length. The cell count check above only catches rows that end up longer or shorter than the header.
  • Running in Node. csvBatches works with a Node 22 Blob, as our tests show, but Node 22 has no global Worker (the test checks this), so importCsv does not run there. Use csvBatches directly.
