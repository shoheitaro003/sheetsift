How to parse European number formats in JavaScript

2026-11-07

A customer in Germany uploads a CSV with a price column. The first value is 1.234,56. Your importer calls parseFloat, stores 1.234, and nobody notices until an invoice is off by a factor of a thousand.

parseFloat("1.234,56"); // 1.234   (wrong, and no error)
Number("1.234,56");     // NaN
Number("1,234.56");     // NaN
parseFloat("1,234.56"); // 1       (wrong, and no error)

JavaScript can format numbers for any locale with Intl.NumberFormat, but it has no matching parse function. This post builds one in five steps. By the end you can turn 1.234,56, 1 234,56 € or (1,234.56) into the right number, and flag the cells you cannot read instead of guessing. Every function, and every input and output quoted below, is checked by our test file.

Our earlier post on why CSV importers break on real Excel files handles the simple case in five lines. This one covers what that version gets wrong: spaces and apostrophes as separators, negative values written four different ways, and columns where a single value cannot tell you the format.

The formats you will actually see

Written asLocales (Intl.NumberFormat)
1,234,567.89en-US, en-GB, ja-JP
1.234.567,89de-DE, it-IT, es-ES, nl-NL, pt-BR
1 234 567,89fr-FR (the space is a narrow no-break space, U+202F)
1'234'567.89de-CH
12,34,567.89en-IN (Indian grouping)

Each row is what Intl.NumberFormat produces in Node.js for 1234567.89, and our tests check every one. Smaller numbers are not always grouped: it-IT, es-ES and pl-PL format 1234.56 as 1234,56. So never expect a separator in every value.

Negative numbers add more variants: -1.234,56, the Unicode minus sign − (U+2212), accounting brackets (1,234.56), and a minus at the end, 1.234,56-. Some systems export the last form, which is why tools exist to convert it in Excel (ASAP Utilities, 2007, updated 2021).

Step 1: separate the sign and remove the noise

First remove what is not part of the number: one known currency symbol or code at either end, and the sign. The currency is removed again after the brackets and after the minus, so (€5), €(5) and -€5 all work. Then check spaces and apostrophes. They are only allowed as thousands separators, between groups of three digits. The function returns the sign and a "body" of digits, dots and commas, or null if the cell is not clearly a number.

const CURRENCY = "R\\$|[$€£¥₹₽₩円]|kr\\.?|zł|EUR|USD|GBP|CHF|JPY|SEK|NOK|DKK|PLN|CZK|BRL|INR|CAD|AUD";
const CURRENCY_START = new RegExp(`^(?:${CURRENCY})\\s*`, "i");
const CURRENCY_END = new RegExp(`\\s*(?:${CURRENCY})$`, "i");
const MINUS = /^[-\u2212]\s*|\s*[-\u2212]$/; // -5, 5- and the minus sign U+2212
const GROUP_SPACE = "[ \u00a0\u202f\u2009'’]"; // space, no-break spaces, thin space, apostrophes
const SPACED_GROUPS = new RegExp(`^[1-9]\\d{0,2}(${GROUP_SPACE})\\d{3}(?:\\1\\d{3})*(?:[.,]\\d+)?$`); // 1 234,56

function splitSign(raw) {
  let t = String(raw ?? "").replace(/[\u200e\u200f\u061c]/g, "").trim(); // direction marks (he-IL)
  let negative = false, signs = 0, currencies = 0;
  const stripCurrency = () => {
    for (const re of [CURRENCY_START, CURRENCY_END]) {
      const next = t.replace(re, "");
      if (next !== t) { currencies++; t = next; }
    }
  };
  stripCurrency();
  if (/^\(.+\)$/.test(t)) { negative = true; signs++; t = t.slice(1, -1).trim(); stripCurrency(); }
  if (MINUS.test(t)) { negative = true; signs++; t = t.replace(MINUS, ""); }
  else if (t.startsWith("+")) t = t.slice(1);
  stripCurrency();
  if (signs > 1 || currencies > 1) return null; // "(-5)" or "$5€" is a mistake, not a number
  if (/[\s'’]/.test(t)) {
    if (!SPACED_GROUPS.test(t)) return null;    // "10 20", "1\n234", "030 123", "2,5 Mio"
    t = t.replace(new RegExp(GROUP_SPACE, "g"), "");
  }
  return /^[\d.,]*\d[\d.,]*$/.test(t) ? { negative, body: t } : null;
}

Each restriction blocks a real way to get a wrong number:

  • Only known currencies are removed. A rule like "drop any three letters" turns 2,5 Mio (2.5 million in a German report) into 2.5, and ISO9001 into 9001. Here both are rejected. Add the currencies your users actually have.
  • Spaces and apostrophes must separate groups of three, the same way throughout. 1 234,56 and 1'234.50 pass. 10 20, 1 234'567 and 030 123 456 (a leading zero) are rejected, and so is a cell with two values on two lines, because tabs and line breaks never count as separators.
  • Two signs or two currencies are an error. (-5) is a typo, not plus five. $5€ is not a price.

Step 2: turn the body into a number, strictly

Once you know which character is the decimal separator, the other one can only be a thousands separator. Enforce that: groups of three digits, a first group that does not start with zero, at most one decimal separator, and no thousands separator after it.

const GROUPED = { ".": /^[1-9]\d{0,2}(\.\d{3})+$/, ",": /^[1-9]\d{0,2}(,\d{3})+$/ };
const INDIAN = /^[1-9]\d?(,\d{2})*,\d{3}$/; // 12,34,567: only accepted for Indian locales

function toNumber({ negative, body }, decimal, { indian = false } = {}) {
  const group = decimal === "," ? "." : ",";
  const [int, frac, extra] = body.split(decimal);
  if (extra !== undefined || frac === "") return null;         // "1,2,3" or "1,"
  if (frac !== undefined && frac.includes(group)) return null;  // "1,23.4"
  const grouped = GROUPED[group].test(int) || (indian && group === "," && INDIAN.test(int));
  if (int.includes(group) && !grouped) return null;             // "1.23" or "030.123"
  const digits = int.split(group).join("");
  if (/^0\d/.test(digits)) return null;                         // "01067": a code, not an amount
  const plain = digits + (frac !== undefined ? "." + frac : "");
  if (plain.replace(/\D/g, "").length > 15) return null;        // too long to be sure it is exact
  const n = Number(plain);
  if (!Number.isFinite(n)) return null;
  return negative && n !== 0 ? -n : n;
}

With a comma as decimal separator, 1.23 returns null rather than 123. A leading zero also means "not an amount": the ID 030.123.456 and the German postcode 01067 both return null, while 0,5 is fine. So does 1, with nothing after the separator. Indian grouping (12,34,567) is only accepted when you ask for it, because in any other locale two-digit groups are a typo.

The length check matters for IDs. JavaScript numbers are 64-bit floats, so Number("12345678901234567891") gives 12345678901234567000. A value with more than 15 digits is rejected instead of silently rounded. Some of those would still be exact, but the simple limit is safe. Keep long IDs as strings.

A rejected cell can be shown to the user. A wrong number goes straight into your database.

Step 3: when you know the locale

If the user has told you their locale (an account setting, or a choice on the import screen), ask Intl.NumberFormat which separators it uses. formatToParts splits a formatted number into labelled pieces, including group and decimal. The result is cached, so each locale is set up only once, not once per cell.

const separatorCache = new Map();

function localeSeparators(locale) {
  if (!separatorCache.has(locale)) {
    let info = null;
    try {
      const format = new Intl.NumberFormat(locale);
      const parts = format.formatToParts(1234567.891);
      const find = (type) => parts.find((p) => p.type === type)?.value ?? "";
      info = { group: find("group"), decimal: find("decimal"), indian: format.format(1234567) === "12,34,567" };
    } catch {
      info = null; // not a valid locale string
    }
    separatorCache.set(locale, info);
  }
  return separatorCache.get(locale);
}

function readNumber(raw, { decimal, indian = false }) {
  if (typeof raw === "number") return Number.isFinite(raw) ? raw : null; // already a number
  if (decimal !== "." && decimal !== ",") return null; // e.g. "٫" in ar-EG: not handled here
  const s = splitSign(raw);
  return s ? toNumber(s, decimal, { indian }) : null;
}

function parseLocaleNumber(raw, locale) {
  const separators = localeSeparators(locale);
  return separators ? readNumber(raw, separators) : null;
}

What readNumber adds to steps 1 and 2:

  • Real numbers pass through. A typed cell from a spreadsheet library is already a JavaScript number. Converting it to a string and reading it as German would turn 1.234 into 1234.
  • Only the decimal separator comes from the locale. Any of the group styles from step 1 is accepted. This matters because Intl groups de-AT, fr-FR and pl-PL with no-break spaces, so a strict check would reject 1.234,56 there. Accepting any group style keeps it working in all three.
  • Unsupported locales return null. That covers locales whose decimal separator is neither a dot nor a comma, such as ar-EG, and invalid locale strings, which would otherwise make Intl throw.

parseLocaleNumber("1.234,56", "de-DE") returns 1234.56, and the same string with "en-US" returns null. Our test also formats -1234567.891 in eleven locales and checks that parsing gives the same number back.

Don't infer the file's format from the visitor's language settings. An accountant in London can easily upload an export from the German office.

Step 4: when you don't know the locale, look at the whole column

One value can be ambiguous; a column often is not. 1,234 could be one thousand two hundred thirty-four or one point two three four. But if the same column also contains 12,5 and 1.234,56, the answer is clear. Each value casts a vote. The column gets a format only if at least two values vote for it and none votes against.

function decimalVote(body) {
  const dot = body.lastIndexOf("."), comma = body.lastIndexOf(",");
  let vote = null;
  if (dot >= 0 && comma >= 0) vote = dot > comma ? "." : ",";         // 1.234,56 or 1,234.56
  else if (dot >= 0 || comma >= 0) {
    const sep = dot >= 0 ? "." : ",", other = sep === "." ? "," : ".";
    const [int, frac] = body.split(sep);
    if (body.indexOf(sep) !== body.lastIndexOf(sep)) vote = other;      // 1.234.567: grouping
    else if (frac.length !== 3 || int === "" || int === "0") vote = sep; // 12,5 / 0,125 / ,5
    // else 1,234 or 1.234: could be either, no vote
  }
  // A vote only counts if the value is valid under it, so 07.11.2026 never votes.
  return vote && toNumber({ negative: false, body }, vote) !== null ? vote : null;
}

function columnVotes(values) {
  const votes = { ".": 0, ",": 0 };
  for (const v of values) {
    if (typeof v === "number") continue; // real numbers carry no format
    const s = splitSign(v);
    const vote = s && decimalVote(s.body);
    if (vote) votes[vote]++;
  }
  return votes;
}

function detectDecimalSeparator(values, minVotes = 2) {
  const votes = columnVotes(values);
  if (votes["."] && votes[","]) return null;  // contradictory: ask the user
  const sep = votes["."] ? "." : ",";
  return votes[sep] >= minVotes ? sep : null; // one value is not enough evidence
}

The rules per value:

  • Both a dot and a comma: the last one is the decimal separator.
  • The same separator twice (1.234.567): it is a thousands separator.
  • One separator not followed by exactly three digits (12,5, 99,90): it is the decimal separator.
  • One separator after a lone zero (0,125): decimal, because a thousands separator never follows a lone zero.
  • Exactly three digits after a single separator (1,234): no vote. The value alone cannot decide.
  • A value that is not valid under its own vote, such as the date 07.11.2026, does not vote.

Why at least two votes? A column of 1,500, 2,500 and 3,25 has one value that says "decimal comma". If that value is a typo, trusting it would turn the other two into 1.5 and 2.5. Raise minVotes for long files.

Some values that are not amounts still vote: short dates without a leading zero (7.11), version numbers (1.10) and IP addresses (192.168.100.200). Run this only on columns you have already identified as numbers, not on every column of the file.

Step 5: put it together for an import

If the user chose a locale, use it, unless even one value in the column contradicts it. If nobody chose, use the data, but only when it is clear. In every other case, return a reason and ask.

function parseNumberColumn(values, chosenLocale) {
  const ask = (reason) => ({ decimal: null, numbers: null, ask: reason });
  let separators;
  if (chosenLocale) {
    separators = localeSeparators(chosenLocale);
    if (!separators || !/^[.,]$/.test(separators.decimal)) return ask("locale not supported");
    const other = separators.decimal === "," ? "." : ",";
    if (columnVotes(values)[other] > 0) return ask("data disagrees with the chosen locale");
  } else {
    const decimal = detectDecimalSeparator(values);
    if (!decimal) return ask("no clear format");
    separators = { decimal, group: decimal === "," ? "." : "," };
  }
  // null in numbers: the cell is empty or not a number, so flag it in the preview
  return { decimal: separators.decimal, numbers: values.map((v) => readNumber(v, separators)), ask: null };
}

For a German export with 1.234,56, -99,90 €, 1.000-, an empty cell and n/a, this returns [1234.56, -99.9, -1000, null, null]. Only the first two values vote (1.000- has three digits after its only separator, so it can't), and two votes are enough. Remove either of them and the function asks instead. The two null cells are the ones to highlight in your preview.

If the user chose de-DE but the column contains 9.99, the result is ask: "data disagrees with the chosen locale", so 1,234 is never quietly read as 1.234.

One case no code can solve: a German export where every value looks like 1.234, 2.500 or 12.000, uploaded by a user who chose en-US. Nothing in the data tells the two readings apart, so the user's choice wins and you get 1.234, 2.5 and 12. Show a preview of the parsed numbers before saving, so the user can spot it.

What this does not cover

  • Scientific notation such as 1,5E+03. These cells are rejected.
  • Scale words such as Mio, TSD or k. These cells are rejected. If your users write them, multiply after parsing, per column.
  • Other digits, such as Arabic ١٢٣ or full-width １２３. These are rejected too. To accept them, map each digit to 0–9 before step 1. (Invisible direction marks, which he-IL puts before negative numbers, are already removed.)
  • The en dash as a minus sign (–5). Rejected. Add – to MINUS if your files use it.
  • A minus at the end in non-financial columns. 2020- becomes -2020. If a column is not from an accounting export, remove the trailing-minus rule from MINUS.
  • Percentages. Strip % in step 1 and divide by 100 afterwards, but only for columns you know are percentages.
