Map CSV and Excel columns to your fields in JavaScript

2026-11-12

Your importer expects a column called email. The customer's file says E-mail, the next one Email address, and a German one E-Mail-Adresse. A list of exact names misses most of them; a substring check maps Email opt-in, a column of yes/no values, to your email field.

By the end of this post you will have mapColumns(headers, fields), about 220 lines with no dependencies, shown in five parts: paste them in order into one module. It matches headers to your fields by name, uses a few sample values to reject wrong matches, and returns sure: false with a reason for every guess, so your mapping screen only asks the user when it has to. Every function, and every result quoted below, is checked by our test file in Node 22.

Why a list of names and a substring check both fail

This first block only shows the problem; it is not part of the solution. (\u00A0 is written as an escape so you can see it; in a real file it is an invisible character.)

const EMAIL_NAMES = ["email", "e-mail", "email address", "mail"];
const exactMatch = (header) => EMAIL_NAMES.includes(header.trim().toLowerCase());
exactMatch("E-mail");             // true
exactMatch("E-Mail-Adresse");     // false
exactMatch("Email\u00A0address");  // false
exactMatch("Ｅｍａｉｌ");         // false

const looseMatch = (header) => header.toLowerCase().includes("mail");
looseMatch("Mailing address");    // true
looseMatch("Email opt-in");       // true

The exact list fails on spelling it did not foresee, on a no-break space (U+00A0) between the words, and on full-width letters. trim() only helps at the ends: it does remove a byte order mark and no-break spaces there. The substring check finds too much: Mailing address is a postal address.

The fix has three parts: clean both names the same way before comparing, compare whole words instead of substrings, and look at the values before trusting a name.

Step 1: normalize the header

Normalizing means turning every spelling of a name into one standard form. This function runs on the header and on every name you compare it with:

function normalizeHeader(text) {
  return String(text ?? "")
    // Ｅｍａｉｌ -> Email, ﾒｰﾙ -> メール, no-break space -> space
    .normalize("NFKC")
    // zero-width spaces and byte order marks
    .replace(/\p{Cf}/gu, "")
    // signupDate -> signup Date
    .replace(/(\p{Ll})(\p{Lu})/gu, "$1 $2")
    .toLowerCase()
    // é -> e, but the mark in Japanese ド stays
    .normalize("NFD")
    .replace(/(\p{Script=Latin})\p{M}+/gu, "$1")
    .normalize("NFC")
    // punctuation, underscores and runs of spaces -> one space
    .replace(/[^\p{L}\p{N}]+/gu, " ")
    .trim();
}

// Plurals count as the same word. "address" is left alone.
function stem(word) {
  if (/(ss|x|ch|sh)es$/.test(word)) return word.slice(0, -2); // addresses
  if (word.length > 3 && /[^s]s$/.test(word)) return word.slice(0, -1); // plans
  return word;
}
const words = (text) => normalizeHeader(text).split(" ").filter(Boolean).map(stem);
const headerKey = (text) => words(text).join(" ");

Each line handles one kind of difference:

  • normalize("NFKC") is the Unicode compatibility form. It turns full-width Ｅｍａｉｌ into Email, half-width katakana ﾒｰﾙｱﾄﾞﾚｽ into メールアドレス, and a no-break space into a normal space.
  • \p{Cf} matches format characters: zero-width spaces and byte order marks. They are invisible and survive NFKC, so they are removed. (A byte order mark is U+FEFF at the very start of a file; if your parser keeps it, it becomes part of the first header.)
  • The camelCase split runs before lowercasing, so signupDate, sign_up_date and SIGNUP DATE end up as words.
  • Accents are removed only from Latin letters, so Téléphone becomes telephone. Removing every combining mark would also strip the voicing mark from Japanese ド.
  • Everything that is not a letter or a digit becomes a space: MRR ($) becomes mrr, and E-mail becomes e mail.

words() also removes a plural ending, so Plans matches plan and Addresses matches address. The rule is crude (status becomes statu), but these keys are only compared, never shown, and both sides get the same treatment. What to watch is two names of different fields that become one, such as new and news. Our tests check the names in step 3; when you add aliases, check that headerKey gives no duplicates across fields.

Step 2: compare a header with one name

compareNames returns a score from 0.6 to 1, or null when the names do not match:

// True when b is a with one letter changed, added or removed,
// or with two neighbouring letters swapped.
function oneEditApart(a, b) {
  if (a === b || Math.abs(a.length - b.length) > 1) return false;
  let i = 0;
  while (a[i] === b[i]) i++; // length of the common start
  if (a.length === b.length) {
    return a.slice(i + 1) === b.slice(i + 1) ||
      (a[i] === b[i + 1] && a[i + 1] === b[i] && a.slice(i + 2) === b.slice(i + 2));
  }
  const [longer, shorter] = a.length > b.length ? [a, b] : [b, a];
  return longer.slice(i + 1) === shorter.slice(i);
}

function compareNames(header, name) {
  const h = words(header), n = words(name);
  if (!h.length || !n.length) return null;
  const hJoined = h.join(""), nJoined = n.join("");
  if (hJoined === nJoined) return { score: 1, why: `same as "${name}"` };
  const contained = n.every((w) => h.includes(w));
  if (contained && h.length === n.length) {
    return { score: 0.95, why: `same words as "${name}"` };
  }
  if (contained) {
    return { score: 0.5 + 0.4 * (n.length / h.length), why: `contains "${name}"` };
  }
  const longEnough = Math.min(hJoined.length, nJoined.length) >= 5;
  if (longEnough && oneEditApart(hJoined, nJoined)) {
    return { score: 0.6, why: `spelled like "${name}"` };
  }
  return null;
}

Comparing without spaces is what makes E-mail, eMail and Email equal. The "contains" score falls as the header gets longer than the name, because every extra word is a chance that the column means something else. The typo rule needs five letters because short names are one letter apart by accident: ARR and MRR are different numbers, Mail and Main different columns.

Step 3: describe your fields

Each field has a key, a label, and the other names users give it. Two optional settings use the values: looksLike tests one cell, and findByValues lets a column with no matching name be picked by its values alone.

const looksLikeEmail = (v) => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(String(v).trim());
const looksLikeNumber = (v) =>
  typeof v === "number" || /^[-+(]?[$€£¥]?\s?\d[\d.,\s']*\)?$/.test(String(v).trim());

const FIELDS = [
  { key: "name", label: "Full name", required: true,
    aliases: ["name", "customer name", "contact name", "氏名", "名前"] },
  { key: "email", label: "Email", required: true,
    looksLike: looksLikeEmail, findByValues: true,
    aliases: ["email address", "mail", "e-mail address", "email adresse",
              "メールアドレス", "メール"] },
  { key: "company", label: "Company",
    aliases: ["company name", "organization", "organisation", "会社名"] },
  { key: "phone", label: "Phone",
    aliases: ["phone number", "telephone", "tel", "mobile", "電話番号"] },
  { key: "mrr", label: "MRR", looksLike: looksLikeNumber,
    aliases: ["monthly revenue", "monthly recurring revenue"] },
];

Set findByValues only where values are distinctive. Almost every cell that passes the email test is an email address. A column of numbers could be revenue, a count or an ID, so mrr uses its test only to reject a match: a column called MRR that contains n/a and free is not used.

The alias list is where you put your users' vocabulary. Start with the names in this post, then add the headers your users map by hand (step 5 shows how to keep them). One-word aliases such as name match many headers: File name and Company name both contain it. That is why a match below 0.95 is flagged unless the values confirm it (step 4); here Company name goes to the company field because its exact alias scores 1.

Step 4: assign each column to at most one field

mapColumns takes the header row, your fields, and optionally sample values for each column and the choices users made before. It returns the match for each field, the columns it did not use with a reason, the required fields it could not fill, and an overall sure.

const MIN_SCORE = 0.6;   // weaker name matches are ignored
const SURE_SCORE = 0.95; // weaker name matches need values to confirm them
const CLOSE = 0.1;       // a rival this close makes the choice a guess

// 0 -> "A", 27 -> "AB"
function columnLetter(i) {
  const prefix = i >= 26 ? columnLetter(Math.floor(i / 26) - 1) : "";
  return prefix + String.fromCharCode(65 + (i % 26));
}

// How many sample values pass the field's check (null: nothing to check).
function valueShare(field, values = []) {
  const filled = values.filter((v) => v != null && String(v).trim() !== "");
  if (!field.looksLike || !filled.length) return null;
  const pass = filled.filter(field.looksLike).length;
  const text = `${pass} of ${filled.length} values look like ${field.label}`;
  return { pass, of: filled.length, text };
}

function bestNameMatch(header, field, remembered) {
  const key = headerKey(header);
  if (key && remembered[key] === field.key) {
    return { score: 1, why: "chosen by a user before" };
  }
  let best = null;
  for (const name of [field.key, field.label, ...(field.aliases ?? [])]) {
    const m = compareNames(header, name);
    if (m && (!best || m.score > best.score)) best = m;
  }
  return best;
}

function mapColumns(headers, fields, { samples = [], remembered = {} } = {}) {
  // Columns that matched a field but were not used: column -> { key, why, second }.
  // second: a better column already fills that field.
  const notUsed = new Map();
  const note = (column, key, why, second = false) => {
    if (!notUsed.has(column)) notUsed.set(column, { key, why, second });
  };

  // 1. Pairs whose names match and whose values do not contradict them.
  const pairs = [];
  fields.forEach((field, f) => headers.forEach((header, column) => {
    const best = bestNameMatch(header, field, remembered);
    if (!best || best.score < MIN_SCORE) return;
    const share = valueShare(field, samples[column]);
    if (share && share.pass / share.of < 0.5) {
      return note(column, field.key, `matched by name, but only ${share.text}`);
    }
    const confirmed = share && share.pass / share.of >= 0.9;
    const doubt = share && !confirmed && `only ${share.text}`;
    pairs.push({ f, column, ...best, confirmed, doubt });
  }));

  // 2. Best pairs first; each field and each column is used once.
  pairs.sort((a, b) => b.score - a.score || a.column - b.column || a.f - b.f);
  const byField = Object.fromEntries(fields.map((field) => [field.key, null]));
  const usedBy = new Map(); // column -> field key
  for (const p of pairs) {
    const field = fields[p.f], taken = byField[field.key];
    if (usedBy.has(p.column)) continue;
    if (taken) {
      const where = columnLetter(taken.column);
      const why = `also matches ${field.label}, which column ${where} already fills`;
      note(p.column, field.key, why, true);
      continue;
    }
    // A rival scores almost as well and could still be used: another free column
    // for this field, or another empty field for this column.
    const rival = pairs.find((q) => q !== p && q.score >= p.score - CLOSE && (
      (q.f === p.f && !usedBy.has(q.column)) ||
      (q.column === p.column && !byField[fields[q.f].key])));
    const doubts = [];
    if (p.score < SURE_SCORE && !p.confirmed) doubts.push("weak name match");
    const rivalColumn = rival && columnLetter(rival.column);
    if (rival?.f === p.f) doubts.push(`column ${rivalColumn} matches too`);
    else if (rival) doubts.push(`could also be ${fields[rival.f].label}`);
    if (p.doubt) doubts.push(p.doubt);
    const header = headers[p.column], sure = !doubts.length;
    byField[field.key] = { column: p.column, header, why: p.why, sure, doubts };
    usedBy.set(p.column, field.key);
  }

  // 3. Fields still empty: the one unused column whose values look right (9 in 10).
  for (const field of fields) {
    if (byField[field.key] || !field.findByValues) continue;
    const fits = headers.map((_, column) => column).filter((column) => {
      const share = !usedBy.has(column) && valueShare(field, samples[column]);
      return share && share.pass / share.of >= 0.9;
    });
    if (fits.length !== 1) {
      const why = `values look like ${field.label}, but so do other columns`;
      fits.forEach((column) => note(column, field.key, why));
      continue;
    }
    const [column] = fits, header = headers[column];
    const why = `values look like ${field.label}`;
    const doubts = ["matched by its values, not its name"];
    byField[field.key] = { column, header, why, sure: false, doubts };
    usedBy.set(column, field.key);
  }

  const unmatched = headers
    .map((header, column) => ({ column, header }))
    .filter(({ column }) => !usedBy.has(column))
    .map((c) => ({ ...c, why: notUsed.get(c.column)?.why ??
      (normalizeHeader(c.header) ? "no field has this name" : "empty header") }));
  const missing = fields.filter((f) => f.required && !byField[f.key])
    .map((f) => f.key);
  // A person should look when a field stayed empty although a column's name
  // matched it, or when a second column matches a filled field (Email, Email 2).
  const needsLook = unmatched.some(({ column }) => {
    const n = notUsed.get(column);
    return n && (n.second || !byField[n.key]);
  });
  const allSure = Object.values(byField).every((m) => !m || m.sure);
  const sure = !missing.length && !needsLook && allSure;
  return { byField, unmatched, missing, sure };
}

It works in three passes:

  1. Collect pairs. For each field and column, keep the best name score of 0.6 or more. If fewer than half of the sample values pass looksLike, drop the pair; if fewer than 9 in 10 pass, keep it with a doubt; if 9 in 10 or more pass, the values confirm it. Blank cells are not counted.
  2. Assign the best pairs first. Sorting by score means Email (1) wins over Email opt-in (0.63), whichever comes first in the file. A match is not sure when its name score is below 0.95 and no values confirm it, or when another free column or field scores within 0.1 of it. So Primary email is a guess until its values look like email addresses. That catches two email columns, and First name next to Last name when you only have a full-name field. So Email next to E-mail (both 1) is a guess. A second match more than 0.1 weaker, such as Work email (0.7) next to Email, is left unused, and it still makes the overall result unsure, so its data is not dropped without the user seeing it.
  3. Use values for fields still empty. For fields with findByValues, a column is picked only if it is the single unused column where 9 in 10 values pass. Two such columns (Contact and Backup contact) leave the field empty: there is no way to tell which one the user means.

The overall result is sure only when every required field is filled, every match is sure, no field was left empty after a column's name matched it, and no unused column matches a filled field. With the fields from step 3, our tests give these results (? marks a match with sure: false):

Step 5: show the mapping screen, then remember the answer

Your parser gives you rows; the header row comes from your own detection (see detecting the header row). The value checks use the first 50 data rows: a default we chose so that a few odd cells do not decide, while large files stay fast. applyMapping then turns rows into records keyed by your field names, skipping rows whose mapped cells are all blank:

// rows: arrays of cells from your CSV or Excel parser.
// headerRow: the index of the header row.
function suggestMapping(rows, headerRow, remembered = {}) {
  const headers = rows[headerRow] ?? [];
  // 50 data rows are enough to check the values.
  const firstRows = rows.slice(headerRow + 1, headerRow + 51);
  const samples = headers.map((_, column) => firstRows.map((row) => row?.[column]));
  return mapColumns(headers, FIELDS, { samples, remembered });
}

// Rows whose mapped cells are all blank are skipped.
function applyMapping(rows, headerRow, byField) {
  const used = Object.entries(byField).filter(([, match]) => match);
  const cell = (row, match) => row?.[match.column] ?? "";
  const toRecord = (row) =>
    Object.fromEntries(used.map(([key, match]) => [key, cell(row, match)]));
  return rows.slice(headerRow + 1)
    .filter((row) => used.some(([, match]) => String(cell(row, match)).trim() !== ""))
    .map(toRecord);
}

When result.sure is true, import without asking. Otherwise show one line per field with the chosen column preselected, and put the doubts and the unmatched reasons next to it, for example column C matches too or matched by name, but only 0 of 2 values look like Email. List missing required fields first. Show unmatched even when the result is sure: a column whose name matches no field (Status, say) does not make the result unsure, and it is not imported.

After the user confirms, store their choices so the same export maps by itself next time:

// After the user confirms the mapping screen, store their choices
// (in your database or in localStorage).
function rememberMapping(remembered, headers, byField) {
  for (const [key, match] of Object.entries(byField)) {
    const header = match && headerKey(headers[match.column]);
    if (header) remembered[header] = key; // blank headers are not remembered
  }
  return remembered;
}

Pass the stored object back as remembered. It is keyed by the normalized header (blank headers are skipped), so Kontakt chosen once also matches KONTAKT later, and it is plain JSON. A remembered choice is still rejected when the values contradict it.

Keep one object per customer in your database: it stores every confirmed column, and two customers can use Contact for different fields. localStorage works for a single browser.

What this does not cover

  • Meaning without shared words. Revenue per month does not match monthly revenue, and Kunde does not match customer. Aliases or remembered choices handle these; matching by meaning needs a synonym list or a language model.
  • One field from several columns, or several fields from one. Joining First name and Last name, or splitting Yui Tanaka <yui@example.jp>, is a transform after mapping.
  • Headers over two rows, such as Billing above Email. Join the two rows into one header first.
  • Japanese or Chinese headers with extra words, as in the table above.
  • Thorough value checks. looksLikeNumber rejects 12.3%, and there is no check for phone numbers, so Phone and Mobile columns are told apart by name only. Write checks for the formats your fields accept.
  • Parsing the values. The checks here only decide whether a column fits. Reading the numbers and dates is covered in our posts on European number formats and Excel dates.
