Read Shift_JIS, Windows-1252 and UTF-16 CSV files in JavaScript

2026-11-11

A customer uploads a CSV and your import screen shows M�ller, or a column of Japanese names turns into “ú–{. Nothing threw an error. The file was not UTF-8, and file.text() read it as UTF-8 anyway.

By the end of this post you will have decodeCsv(bytes, legacy), about 150 lines with no dependencies, shown in four parts below: paste them in order into one module and nothing else is needed (the test file has them in one piece). It reads UTF-8, UTF-16 with or without a byte order mark, and the legacy encodings you list (such as Windows-1252 or Shift_JIS). It returns the encoding it used, and sure: false with a reason when the bytes fit several of the encodings you list, or none of them cleanly, so your UI can ask instead of importing garbage. It cannot notice an encoding that is missing from your list; the table in step 4 shows what happens then. Every result quoted below is checked by our test file in Node 22, and the browser-only results by a Chromium test.

Why it happens

A CSV file is only bytes. Nothing in it says which encoding, the table that maps bytes to characters, was used to write it. é is the single byte E9 in Windows-1252 and the two bytes C3 A9 in UTF-8. file.text() and a plain new TextDecoder() both assume UTF-8 and put the replacement character � wherever the bytes are not valid UTF-8:

const cafe = new Uint8Array([0x43, 0x61, 0x66, 0xe9]); // "Café" saved as Windows-1252
await new Blob([cafe]).text();                 // "Caf\uFFFD"
new TextDecoder().decode(cafe);                // "Caf\uFFFD"
new TextDecoder("windows-1252").decode(cafe);  // "Café"

const nihon = new Uint8Array([0x93, 0xfa, 0x96, 0x7b]); // "日本" saved as Shift_JIS
new TextDecoder("shift_jis").decode(nihon);    // "日本"
new TextDecoder("windows-1252").decode(nihon); // "“ú–{"

The last line is the dangerous one. The Shift_JIS bytes for 日本 are also valid Windows-1252, so the wrong decoder returns four ordinary-looking characters and no error. Detection therefore needs two checks: are the bytes valid in an encoding, and does the result look like text a person wrote?

Four traps in TextDecoder

TextDecoder is the built-in decoder in browsers and Node. Four of its behaviours surprise people. Each line below prints what its comment says:

// 1. Several labels give the same decoder.
new TextDecoder("latin1").encoding;      // "windows-1252"
new TextDecoder("iso-8859-1").encoding;  // "windows-1252"
new TextDecoder("ascii").encoding;       // "windows-1252"
new TextDecoder("sjis").encoding;        // "shift_jis"
new TextDecoder("windows-31j").encoding; // "shift_jis"
new TextDecoder("utf-16").encoding;      // "utf-16le"
new TextDecoder("utf-32");               // throws RangeError

// 2. A byte order mark only helps if you picked the right decoder already.
// "Hi" in UTF-16LE, with a BOM:
const hi = new Uint8Array([0xff, 0xfe, 0x48, 0x00, 0x69, 0x00]);
new TextDecoder("utf-16le").decode(hi);  // "Hi"
new TextDecoder("utf-8").decode(hi);     // "\uFFFD\uFFFDH\u0000i\u0000"

// 3. Windows-1252 accepts every byte, so "no error" proves nothing.
const strict1252 = new TextDecoder("windows-1252", { fatal: true });
strict1252.decode(new Uint8Array([0x81, 0x8d])); // "\u0081\u008d"

// 4. Chunks decoded separately break characters that cross a chunk boundary.
const tokyo = new TextEncoder().encode("東京"); // 6 bytes, 3 per character
const decoder = new TextDecoder();
decoder.decode(tokyo.slice(0, 4)) + decoder.decode(tokyo.slice(4)); // "東\uFFFD\uFFFD\uFFFD"
decoder.decode(tokyo.slice(0, 4), { stream: true }) + decoder.decode(tokyo.slice(4)); // "東京"
  1. Labels are aliases. Asking for latin1, iso-8859-1 or ascii gives you the Windows-1252 decoder, and sjis or windows-31j gives Shift_JIS. Check decoder.encoding if you log what you used. UTF-32 has no decoder at all.
  2. A byte order mark does not pick the decoder. A byte order mark (BOM) is a short signature at the start of a Unicode file: EF BB BF for UTF-8, FF FE for UTF-16LE, FE FF for UTF-16BE. A UTF-16 decoder removes a matching one, but a UTF-8 decoder turns a UTF-16 BOM into replacement characters, so you have to look at the first bytes yourself. Blob.text() is no help either, and it differs between runtimes: in our tests in November 2026 it decoded a UTF-16LE file with a BOM correctly in Chromium (versions 129 and 153) but returned replacement characters in Node 22. Do not rely on it; check the first bytes yourself.
  3. Windows-1252 never fails. In TextDecoder, every one of its 256 bytes maps to a character; the five bytes 81, 8D, 8F, 90 and 9D map to invisible control characters. So fatal: true, which makes the decoder throw on invalid bytes, rules nothing out for Windows-1252. It does rule out a lot for multi-byte encodings such as Shift_JIS and UTF-8.
  4. Chunks need stream: true. In UTF-8 and Shift_JIS one character can take several bytes. Decode chunks separately and a character split across two chunks becomes replacement characters. Pass { stream: true } on every call except the last, as the last line shows; the decoder then keeps the incomplete character for the next chunk.

Step 1: Unicode files first

Check for a byte order mark before anything else, because it is the only part of the file that states an encoding. UTF-32 marks come first in the list, since FF FE 00 00 also starts with the UTF-16LE mark.

const BOMS = [ // byte order marks; UTF-32 before UTF-16, because FF FE starts both
  { bytes: [0xef, 0xbb, 0xbf], encoding: "utf-8" },
  { bytes: [0xff, 0xfe, 0x00, 0x00], encoding: null }, // UTF-32LE: TextDecoder cannot read it
  { bytes: [0x00, 0x00, 0xfe, 0xff], encoding: null }, // UTF-32BE
  { bytes: [0xff, 0xfe], encoding: "utf-16le" },
  { bytes: [0xfe, 0xff], encoding: "utf-16be" },
];

function sniffBom(bytes) {
  return BOMS.find((bom) => bom.bytes.every((b, i) => bytes[i] === b)) ?? null;
}

// UTF-16 without a BOM: commas, digits and line breaks are 2 bytes with one zero,
// so zeros pile up on one side of each byte pair ("," is 2C 00 in UTF-16LE).
function guessUtf16(bytes) {
  const end = Math.min(bytes.length, 4096) & ~1; // whole 2-byte units only
  let evenZeros = 0, oddZeros = 0;
  for (let i = 0; i < end; i += 2) {
    if (bytes[i] === 0) evenZeros++;
    if (bytes[i + 1] === 0) oddZeros++;
  }
  const units = end / 2;
  const enough = Math.max(units / 10, 4); // a stray zero byte in a short file is not UTF-16
  if (oddZeros >= enough && evenZeros < oddZeros / 4) return "utf-16le";
  if (evenZeros >= enough && oddZeros < evenZeros / 4) return "utf-16be";
  return null;
}

function decodeStrict(bytes, encoding) {
  try {
    return new TextDecoder(encoding, { fatal: true }).decode(bytes);
  } catch {
    return null; // the bytes are not valid in this encoding
  }
}

UTF-16 files without a BOM have a strong fingerprint: every ASCII character, including the commas, digits and line breaks a CSV is full of, takes two bytes and one of them is zero. guessUtf16 counts zeros at even and odd positions in the first 4 KB. One side needs at least 4 zeros and more than a tenth of the pairs, so a stray zero byte in a short file does not count. It also needs four times as many zeros as the other side, because Japanese characters such as 一 (00 4E) put an occasional zero on the other side.

decodeStrict returns null instead of throwing, so the next steps can try one encoding after another.

Step 2: UTF-8, or damaged UTF-8

If strict UTF-8 decoding succeeds, use it. Plain ASCII text (letters, digits, punctuation, tabs and line breaks) reads the same in every legacy encoding listed here, so nothing is lost. A short legacy file can still be valid UTF-8 by chance; none of our samples is, but see the limits at the end.

If it fails, do not jump straight to a legacy encoding. A file that someone assembled from two exports can be UTF-8 with one pasted line in Windows-1252. Decoding the whole file as Windows-1252 would then break every other line. utf8Damage measures how much of the non-ASCII data is valid UTF-8 and where the first broken byte is. It follows the UTF-8 rules closely enough to reject overlong forms and surrogates, which a quick “lead byte plus continuation bytes” check would accept:

// How many bytes a UTF-8 character starting with this byte has (0: not a valid first byte).
function utf8SequenceLength(b) {
  if (b < 0x80) return 1;
  if (b >= 0xc2 && b <= 0xdf) return 2;
  if (b >= 0xe0 && b <= 0xef) return 3;
  if (b >= 0xf0 && b <= 0xf4) return 4;
  return 0;
}

// After these first bytes the second byte has a narrower range: no overlong forms,
// no surrogates (ED A0-BF), nothing above U+10FFFF (F4 90-BF).
const SECOND_BYTE = { 0xe0: [0xa0, 0xbf], 0xed: [0x80, 0x9f], 0xf0: [0x90, 0xbf], 0xf4: [0x80, 0x8f] };

// Share of non-ASCII bytes that form valid UTF-8 sequences, and where the first bad byte is.
// Close to 1: a UTF-8 file with a few broken bytes. Close to 0: another encoding.
function utf8Damage(bytes) {
  let valid = 0, invalid = 0, firstInvalid = -1;
  for (let i = 0; i < bytes.length; ) {
    const b = bytes[i];
    if (b < 0x80) { i++; continue; }
    const length = utf8SequenceLength(b);
    const [low, high] = SECOND_BYTE[b] ?? [0x80, 0xbf];
    let ok = length > 0 && bytes[i + 1] >= low && bytes[i + 1] <= high;
    for (let k = 2; ok && k < length; k++) ok = (bytes[i + k] & 0xc0) === 0x80; // 10xxxxxx
    if (ok) { valid += length; i += length; continue; }
    if (firstInvalid < 0) firstInvalid = i;
    invalid++;
    i++;
  }
  return { share: valid / (valid + invalid || 1), firstInvalid };
}

// An upload limit or a broken copy can cut a file in the middle of a character.
// Returns where that incomplete last character starts, or -1.
function cutCharacterAtEnd(bytes) {
  for (let back = 1; back <= 3 && back <= bytes.length; back++) {
    const b = bytes[bytes.length - back];
    if ((b & 0xc0) === 0x80) continue; // 10xxxxxx: a continuation byte, keep looking for the first byte
    const length = utf8SequenceLength(b);
    return length > back ? bytes.length - back : -1;
  }
  return -1;
}

function lineAt(bytes, offset) { // counts LF, CRLF and CR-only line breaks
  let line = 1;
  for (let i = 0; i < offset; i++) if (bytes[i] === 0x0a || (bytes[i] === 0x0d && bytes[i + 1] !== 0x0a)) line++;
  return line;
}

When 90% or more is valid, decodeCsv keeps UTF-8 and reports the line of the first bad byte. Your user can fix one line far more easily than a whole column of mojibake (text decoded with the wrong encoding). The line is a physical line, counted by line breaks, not a CSV record: a quoted cell with a line break inside makes the two differ. This needs enough valid UTF-8 around the damage: a file whose only other non-ASCII character is one é falls below 90% and goes on to the legacy step. Our Shift_JIS and EUC-JP samples score between 0 and 0.31 on this measure, and our Windows-1252 samples score 0.

One more UTF-8 case needs its own check. An upload size limit or a broken copy can cut a file in the middle of a character, so the last one to three bytes are an incomplete sequence. cutCharacterAtEnd finds that sequence; if everything before it is valid UTF-8 and contains non-ASCII text, decodeCsv keeps UTF-8 and says the file was cut off. The non-ASCII condition matters: a Windows-1252 file that is plain ASCII apart from a final é (E9, which also starts a 3-byte UTF-8 sequence) must still go to the legacy step.

Step 3: legacy encodings, checked twice

For the encodings you list, the first check is validity with fatal: true. That alone separates many files: three of our four Windows-1252 samples are not valid Shift_JIS, and four of our five Shift_JIS samples are not valid EUC-JP. But Windows-1252 accepts every byte, so it always survives, and GB18030, a Chinese encoding, accepted four of the five Shift_JIS samples too. The second check scores what the decoded text looks like:

// Symbols that wrongly decoded Japanese produces often and real Western text almost never uses.
const RARE_SYMBOLS = /[\u0192\u02c6\u02dc\u2020\u2021\u2030\u00a4\u00a6\u00a8\u00af\u00b8\u2039\u203a]/;

function charClass(c) {
  if (c === undefined || c < "\u0080") return /[0-9]/.test(c ?? "") ? "digit" : "ascii";
  if (/[\p{Cc}\p{Co}\p{Cn}\uFFFD]/u.test(c) || RARE_SYMBOLS.test(c)) return "junk"; // controls, private use, unassigned
  if (/[\u3000-\u30ff\uff01-\uff60]/.test(c)) return "kana"; // kana, plus the CJK and full-width punctuation used with it
  if (/\p{Script=Han}/u.test(c)) return "han";
  if (/[\uff61-\uff9f]/.test(c)) return "halfKana";
  if (/\p{L}/u.test(c)) return "letter";
  if (/[\p{Pi}\p{Pf}]/u.test(c)) return "quote"; // “ ” ‘ ’ « »
  return "symbol";
}

// Does a non-ASCII character of this class look real next to these neighbours?
function fitsBetween(cls, sides, hasKana) {
  const latin = (s) => s === "ascii" || s === "digit" || s === "letter" || s === "quote";
  switch (cls) {
    case "kana": return true;
    case "han": return hasKana || sides.some((s) => s === "han" || s === "kana" || s === "digit"); // 東京, 100円
    case "halfKana": return sides.includes("halfKana");
    case "letter": // Müller, l’été
    case "quote": return sides.every(latin);
    case "symbol": return sides.every((s) => s === "ascii" || s === "digit"); // 1.234,50 €
    default: return false; // junk
  }
}

// From 0 to 1: the share of non-ASCII characters that sit where real text puts them.
function plausibility(text) {
  const classes = Array.from(text.slice(0, 100000)).map(charClass); // a sample is enough
  const hasKana = classes.includes("kana");
  let nonAscii = 0, good = 0;
  classes.forEach((cls, i) => {
    if (cls === "ascii" || cls === "digit") return;
    nonAscii++;
    const sides = [classes[i - 1] ?? "ascii", classes[i + 1] ?? "ascii"];
    if (fitsBetween(cls, sides, hasKana)) good++;
  });
  return nonAscii === 0 ? 1 : good / nonAscii;
}

plausibility looks only at non-ASCII characters and at their neighbours. Real accented letters and curly quotes sit next to ASCII, other letters or quotes (Müller, l’été). Real symbols such as € or – sit next to ASCII (1.234,50 €). A kanji counts as real when the text also contains kana, or when it stands next to another kanji or a digit, so 東京都,大阪府 and 100円 score 1.

Wrongly decoded bytes produce control characters, private-use characters, symbols packed between other non-ASCII characters, and isolated kanji between Latin letters. RARE_SYMBOLS adds the few characters that Japanese text read as Windows-1252 produces all the time and Western text almost never contains, such as ‰ (the first byte of 円) and †. The cost is that a real ‰ or † in a Western file makes the result not sure. The main Shift_JIS sample in our tests scores 1.00 as Shift_JIS and 0.23 as Windows-1252.

Step 4: put it together

// legacy: the encodings your users' older software writes, most likely first.
function decodeCsv(bytes, legacy = ["windows-1252"]) {
  const result = (encoding, text, sure, reason, options = []) => ({ encoding, text, sure, reason, options });
  const refuse = (reason) => result(null, null, false, reason);

  const startsWith = (...signature) => signature.every((b, i) => bytes[i] === b);
  if (startsWith(0x50, 0x4b, 0x03, 0x04)) return refuse("this is a ZIP file, probably an .xlsx renamed to .csv");
  if (startsWith(0xd0, 0xcf, 0x11, 0xe0)) return refuse("this is an old .xls file renamed to .csv");
  const bom = sniffBom(bytes);
  if (bom && !bom.encoding) return refuse("UTF-32 file: save it as UTF-8 and try again");
  const unicode = bom ? bom.encoding : guessUtf16(bytes);
  if (unicode) {
    const text = decodeStrict(bytes, unicode); // also removes the BOM
    if (text === null) return refuse(`looks like ${unicode} but is not valid ${unicode}`);
    return result(unicode, text, true, bom ? "byte order mark" : "UTF-16 zero-byte pattern");
  }
  if (bytes.includes(0)) return refuse("contains zero bytes: a binary file, or UTF-16 without a byte order mark");

  const utf8 = decodeStrict(bytes, "utf-8");
  if (utf8 !== null) return result("utf-8", utf8, true, "valid UTF-8");

  const options = legacy
    .map((encoding) => ({ encoding, text: decodeStrict(bytes, encoding) }))
    .filter((option) => option.text !== null)
    .map((option) => ({ ...option, score: plausibility(option.text) }))
    .sort((a, b) => b.score - a.score);
  const scores = options.map(({ encoding, score }) => ({ encoding, score })); // for an encoding picker
  const flagUtf8 = (reason) => result("utf-8", new TextDecoder().decode(bytes), false, reason, scores);

  const cut = cutCharacterAtEnd(bytes);
  const before = cut > 0 ? bytes.subarray(0, cut) : null;
  if (before && before.some((b) => b >= 0x80) && decodeStrict(before, "utf-8") !== null)
    return flagUtf8(`UTF-8 cut off in the middle of a character at the end (line ${lineAt(bytes, cut)})`);
  const damage = utf8Damage(bytes);
  if (damage.share >= 0.9) return flagUtf8(`UTF-8 with invalid bytes, first on line ${lineAt(bytes, damage.firstInvalid)}`);

  if (options.length === 0) return refuse(`not valid UTF-8 or ${legacy.join(", ")}`);
  const [best, next] = options;
  if (best.score < 0.9)
    return result(best.encoding, best.text, false, `no encoding gives clean text (best guess: ${best.encoding})`, scores);
  if (next && best.score - next.score < 0.3)
    return result(best.encoding, best.text, false, `${best.encoding} and ${next.encoding} both give clean text`, scores);
  return result(best.encoding, best.text, true, `not UTF-8, clean as ${best.encoding}`, scores);
}

The default candidate list, ["windows-1252"], only suits Western European data. Windows-1252 accepts every byte, so with that default every file decodes as Windows-1252: our Russian sample comes back sure and wrong, and other alphabets can too. Pass your own list.

The result is { encoding, text, sure, reason, options }. A file is sure when the best candidate scores at least 0.9 and beats the next valid one by at least 0.3. When sure is false, encoding and text are only the best guess, and options lists every legacy encoding the bytes are valid in, with its score, for an encoding picker. On a tie the candidate listed first wins.

The thresholds (0.9 and 0.3 here, 90% valid UTF-8 in step 2, the zero-byte ratios in step 1) were chosen against the samples in our tests, not tuned on a large set of real files. Raising them gives more sure: false results and fewer wrong sure ones; lowering them does the opposite. Valid UTF-8 is always reported as sure, which is right for nearly every file but not for the rare short legacy file that happens to be valid UTF-8 (see the limits below).

The not-sure rows show the limits. Shift_JIS bytes can decode cleanly as GB18030 too, as Chinese characters (both score 1.00 for our sample), and a file with only kanji dates reads as plausible Windows-1252 symbols. Windows-1251 and Windows-1252 accept every byte and both produce letters, so with only windows-1252 listed a Russian file comes back as Latin letters and sure: true. The list of candidates is therefore your decision: include every encoding your users' files can arrive in, most likely first, and nothing else.

Using it in an upload form

Read the file as bytes, not text, so you can decode it again if the user picks another encoding:

async function readCsvText(file, legacy) {
  const bytes = new Uint8Array(await file.arrayBuffer());
  const decoded = decodeCsv(bytes, legacy);
  // When decoded.sure is false, show a preview and let the user pick another encoding.
  // decodeAs returns null if the bytes are not valid in the chosen encoding; switching
  // back to the first result always works, even for damaged UTF-8.
  const decodeAs = (encoding) => (encoding === decoded.encoding ? decoded.text : decodeStrict(bytes, encoding));
  return { ...decoded, decodeAs };
}

const { encoding, text, sure, reason, options, decodeAs } = await readCsvText(file, ["windows-1252", "shift_jis"]);

When sure is true, continue with text. When it is false and text is set, do not import yet: show the first few lines, the reason, and a picker filled from options. Call decodeAs when the user changes the choice, so they see the names become readable; it returns null when the bytes are not valid in that encoding, so say so instead of showing replacement characters. Choosing the first result again always works, even for damaged UTF-8. When text is null, show the reason and stop.

For damaged or cut-off UTF-8, show the line number first: fixing that line, or uploading the whole file again, is usually the right answer. options still lists the legacy encodings the bytes are valid in, in case the file is not UTF-8 after all.

What this does not cover

  • Choosing the candidates for you. The function cannot know where your users are. Single-byte encodings for different alphabets (Windows-1250, 1251, 1252) cannot be told apart reliably by this score, as the table shows.
  • Mixed encodings inside one legacy file. Only damaged UTF-8 is detected; a Shift_JIS file with one Windows-1252 line is refused or flagged as unclear, not repaired.
  • Legacy text that happens to be valid UTF-8. It is read as UTF-8. This is possible with short files.
  • Very small files. With only a few non-ASCII characters, one odd character moves the score a lot, so expect more sure: false results on tiny files.
  • UTF-16 without a BOM and with almost no ASCII, for example a single column of Japanese text with no commas. It is not detected as UTF-16; because its line breaks still contain zero bytes, our sample is refused as “a binary file, or UTF-16 without a byte order mark” rather than misread.
  • Bytes that mean different characters in different variants of Shift_JIS, and encodings TextDecoder does not support, such as UTF-32 and EBCDIC.
  • Browsers other than Chromium, where we have not run these checks.
  • Runtimes without the legacy decoders. new TextDecoder(label) throws a RangeError for an encoding the runtime does not support, so try each of your candidates once in every runtime you deploy to.
  • Other legacy encodings, such as Mac Roman. Its bytes are valid Windows-1252 and give plausible letters, so a Mac Roman file comes back wrong and sure unless you list "macintosh" as a candidate; with both listed, the result is not sure.
  • Streaming and very large files. decodeCsv needs the whole file: a slice cut in the middle of a character fails the strict checks. It also decodes the whole file once per candidate, so memory use grows with file size times the number of candidates. Parsing very large files in chunks is a separate topic.
  • False alarms. An accented letter right before …, – or a similar symbol counts against the score, so a short file like Café… comes back not sure, and so does a Western file with a real ‰ or † in it, such as 5‰. Loosening that rule would also accept Japanese text read as Windows-1252.
  • Delimiters, quotes and header rows, which come after decoding. See why CSV importers break on real Excel files and detecting the header row.
